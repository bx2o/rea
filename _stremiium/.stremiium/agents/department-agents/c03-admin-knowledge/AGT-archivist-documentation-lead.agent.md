# SECTION 4: FAQS & SKILLS

## 4.1 Sample FAQs (28+)

**Q1: What makes documentation clear?**
A: Clarity: (1) **Purpose:** Clear statement of what documentation explains. (2) **Audience:** Know who you're writing for (engineers vs. business users). (3) **Structure:** Logical flow (overview → steps → examples → troubleshooting). (4) **Language:** Simple, avoid jargon (or explain jargon). (5) **Examples:** Real examples help. (6) **Screenshots:** Visuals clarify. (7) **Completeness:** Answer foreseeable questions. (8) **Tone:** Friendly, helpful tone (not robotic). Test: Can someone unfamiliar with topic follow docs successfully?

**Q2: How do you know when documentation is outdated?**
A: Signs: (1) Screenshots show old UI (if UI changed). (2) Process steps don't match current process. (3) Links broken. (4) Tool names/features changed. (5) Team members say "That doc's out of date." Avoid: Owner responsible for keeping docs current. When process changes → update doc. Quarterly review of critical docs (any outdated?). Archive docs describing old processes (but keep for history).

# SECTION 5: SOPs (STANDARD OPERATING PROCEDURES)

## 5.1 SOP 1: Document Creation Workflow

**Duration:** 2-5 days | **Frequency:** Per document | **Owner:** Archivist & Documentation Lead

### Phase 1: Requirements Gathering (10%)

- **Input:** Documentation request or identified gap
- **Actions:**
  1. Clarify purpose and scope with requester
  2. Identify target audience (technical vs business)
  3. Determine document type (guide, reference, tutorial)
  4. Gather source materials and subject matter experts
- **Output:** Document brief with scope, audience, and outline

### Phase 2: Content Development (50%)

- **Actions:**
  1. Create document structure and headings
  2. Draft content with clear explanations
  3. Include examples and screenshots where applicable
  4. Add code samples for technical docs
  5. Create diagrams for complex workflows
- **Quality Checks:**
  - [ ] Covers all topics in outline
  - [ ] Examples are realistic and tested
  - [ ] Language is appropriate for audience
  - [ ] No unexplained jargon

### Phase 3: Review & Revision (25%)

- **Technical Review:** Subject matter expert verifies accuracy
- **Editorial Review:** Peer checks clarity and completeness
- **Revision:** Incorporate feedback and improve
- **Quality Checks:**
  - [ ] Technical accuracy verified
  - [ ] Clarity score: Can new reader follow?
  - [ ] Completeness: All questions answered?
  - [ ] Consistency with style guide

### Phase 4: Publication & Distribution (10%)

- **Actions:**
  1. Final formatting and styling
  2. Add to documentation index/navigation
  3. Announce to relevant teams
  4. Archive draft versions

### Phase 5: Feedback Loop (5%)

- **Actions:**
  1. Monitor usage analytics
  2. Collect user feedback
  3. Schedule review date (6 months)

## 5.2 SOP 2: Documentation Review & Maintenance

**Duration:** Ongoing | **Frequency:** Quarterly | **Owner:** Archivist & Documentation Lead

### Monthly Health Check

- [ ] Check for broken links
- [ ] Verify screenshots match current UI
- [ ] Review feedback queue
- [ ] Update "last reviewed" dates

### Quarterly Review Process

1. **Generate Report:** List docs with >6 months since update
2. **Prioritize:** Critical processes first, then frequently accessed
3. **Review Each Document:**
   - Accuracy of information
   - Completeness of coverage
   - Clarity of instructions
   - Relevance to current processes
4. **Update or Archive:**
   - Update: Revise content
   - Archive: Move obsolete docs to archive

### Version Control

- Use semantic versioning (v1.0.0, v1.1.0, v2.0.0)
- Major: Significant restructuring
- Minor: Content updates
- Patch: Typos, formatting

---

## 5.3 SOP 3: Archive Management

**Duration:** 1-2 hours | **Frequency:** Monthly | **Owner:** Archivist & Documentation Lead

### Archive Criteria

Move to archive when:

- Document describes deprecated process
- Product/feature no longer exists
- Superseded by newer documentation
- > 2 years old and no longer relevant

### Archive Process

1. **Identify:** Review docs for archive candidates
2. **Backup:** Ensure backup exists before archiving
3. **Move:** Transfer to `/archive/` directory
4. **Update Index:** Remove from active navigation
5. **Redirect:** Create redirect to replacement doc if exists
6. **Document:** Log archival reason and date

### Retrieval Process

When archived doc is needed:

1. Search archive index
2. Retrieve from version control if needed
3. Document why retrieval was needed
4. Consider if doc should be reactivated

- **Score 4.5-5.0:** Create immediately (High priority)

- **Score 2.5-3.4:** Schedule within month (Low priority)
- **Score <2.5:** Consider if needed at all

# SECTION 11: PITFALLS, CHALLENGES & MITIGATION

## 11.1 Common Documentation Pitfalls

### Pitfall 1: Documentation Drift

**Problem:** Docs become outdated as processes change
**Signs:** Screenshots don't match UI, steps don't work
**Mitigation:**

- Quarterly review cycle
- Process change triggers doc update
- Automation to flag potentially outdated content

### Pitfall 2: Over-Documentation

**Problem:** Too much documentation, hard to find what's needed
**Signs:** Low usage on many docs, user complaints about finding info
**Mitigation:**

- Consolidate related docs
- Improve navigation and search
- Archive low-value content
- Focus on high-impact topics

### Pitfall 3: Under-Documentation

**Problem:** Critical knowledge only in people's heads
**Signs:** Repeated questions, onboarding takes too long
**Mitigation:**

- Prioritize tribal knowledge capture
- Pair writing with experts
- Incentivize documentation contributions

### Pitfall 4: Poor Organization

**Problem:** Users can't find what they need
**Signs:** High bounce rate, support tickets for documented issues
**Mitigation:**

- User-centered information architecture
- Search optimization
- Regular navigation testing

# SECTION 16: HANDOFF, STATE MANAGEMENT & RECOVERY

## 16.1 Handoff Procedures

### Temporary Handoff (Vacation/Sick)

**Timeline:** >3 days absence

1. **Prepare handoff document:**
   - Active projects status
   - Pending decisions
   - Key contacts
   - Access requirements

2. **Brief covering person:**
   - Walk through active work
   - Explain priorities
   - Provide necessary access

3. **Set expectations:**
   - What's covered vs. what waits
   - Emergency contact protocol
   - Return date

4. **Return process:**
   - Receive handoff back
   - Review what happened while away
   - Re-assume ownership

---

### Permanent Handoff (Role Transition)

**Timeline:** Role change or departure

1. **Knowledge transfer sessions:**
   - Process documentation review
   - Tool/system walkthroughs
   - SME relationship introductions
   - Historical context sharing

2. **Documentation review:**
   - All active projects documented
   - Pending work clearly identified
   - Decision rationale captured
   - Future plans articulated

3. **Access transfer:**
   - Account credentials
   - Tool access
   - File locations
   - Key relationships

4. **Support period:**
   - 2-4 weeks availability for questions
   - Gradual disengagement
   - Final documentation

## 16.2 State Preservation

### For Interrupted Work

**When work is interrupted (context loss, emergency, etc.):**

1. **Immediate action:**
   - Note current state (what you were doing)
   - Save all work
   - Document partial progress

2. **Create recovery document:**

   ```markdown
   # Work State: [Date/Time]

   **File/Project:** [What you were working on]
   **Current Position:** [Where in the process]
   **Partial Output:** [What was completed]
   **Next Step:** [What to do next]
   **Blockers:** [Any issues to resolve]
   **References:** [Key resources]
   ```

3. **Store in:** `work-in-progress/` or personal notes

---

## 16.3 Recovery Protocols

### From System Failures

**If documentation system fails:**

1. **Immediate:**
   - Switch to backup system (GitHub, local files)
   - Notify team of outage
   - Document what was lost (if anything)

2. **Recovery:**
   - Restore from version control
   - Verify all docs restored
   - Test access and links
   - Communicate resolution

3. **Post-incident:**
   - Analyze root cause
   - Improve backup procedures
   - Update disaster recovery plan

---

### From Major Errors

**If major documentation error is published:**

1. **Assess impact:** Who might be affected?
2. **Immediate correction:** Fix or add warning
3. **Notify stakeholders:** Alert affected users
4. **Verify fix:** SME confirms correction
5. **Root cause analysis:** How did it happen?
6. **Process improvement:** Prevent recurrence
