## 3.2 Knowledge Management Standard Operating Procedures (SOPs)

### SOP 1: Document Creation & Publishing

**Scope:** New document creation and publishing workflow
**Trigger:** New document request or identified need

**Steps:**

1. **Request & Planning** (1-2 days)
   - Document content needs identified
   - Stakeholders and approvers identified
   - Timeline and resources allocated

2. **Creation** (Varies by complexity)
   - Author creates document following standards
   - Use appropriate template
   - Include all required sections

3. **Technical Review** (2-5 days)
   - Subject matter expert reviews accuracy
   - Technical correctness verified
   - Feedback incorporated

4. **Editorial Review** (1-3 days)
   - Documentation Specialist reviews
   - Style and format compliance checked
   - Grammar and clarity reviewed

5. **Approval** (1-5 days)
   - Stakeholder approval obtained
   - Compliance review if required
   - Final approval documented

6. **Publishing** (1 day)
   - Publish to appropriate repository
   - Set permissions and access
   - Notify stakeholders

7. **Maintenance Planning** (Ongoing)
   - Schedule review date
   - Assign maintenance owner
   - Set update triggers

### SOP 2: Agent Configuration Update

**Scope:** Updating agent system prompts or configurations
**Trigger:** Agent update required

**Steps:**

1. **Change Request** (1 day)
   - Document change rationale
   - Identify affected agents
   - Assess impact

2. **Draft Update** (1-3 days)
   - Create updated agent configuration
   - Follow 16-section format
   - Maintain consistency with other agents

3. **Review** (2-3 days)
   - Knowledge Architect reviews structure
   - Content accuracy review
   - Compliance check

4. **Approval** (1-2 days)
   - Chief-Librarian approval
   - Council Captain approval if cross-council
   - Sparkling Curious notification for major changes

5. **Version Update** (1 day)
   - Update version number
   - Document changes in change log
   - Update last updated date

6. **Deployment** (1 day)
   - Deploy to `.github/agents/`
   - Sync to `.windsurf/rules/` if applicable
   - Verify deployment

7. **Notification** (1 day)
   - Notify affected councils/agents
   - Update documentation
   - Monitor for issues

### SOP 3: Documentation Audit

**Scope:** Comprehensive documentation audit
**Trigger:** Quarterly audit cycle or special request

**Steps:**

1. **Planning** (Week 1)
   - Define audit scope
   - Identify audit team
   - Prepare audit checklist
   - Schedule audit activities

2. **Inventory** (Week 2)
   - Catalog all documentation
   - Map to owners and stakeholders
   - Identify gaps in coverage

3. **Quality Assessment** (Week 3-4)
   - Review docs against quality criteria
   - Identify outdated documentation
   - Check standard compliance
   - Assess accuracy

4. **Compliance Verification** (Week 4)
   - Verify regulatory documentation complete
   - Check approval workflows followed
   - Validate access controls

5. **Report** (Week 5)
   - Compile audit findings
   - Prioritize remediation items

## 4.1 Stremiium Knowledge FAQ

### Documentation Standards

**Q1: What is the 16-section format for agents?**
A: A comprehensive, unconsolidated format with: 0 (Context), 1 (Identity), 2 (Context Setup), 3 (Task Descriptions), 4 (Knowledge Base), 5 (Communication), 6 (Engineering), 7 (Product Requirements), 8 (Architecture), 9 (UX Design), 10 (Tools), 11 (Validation), 12 (Decision-Making), 13 (SubAgent Delegation), 14 (Implementation), 15 (RAG Structure), 16 (Continuous Improvement), plus Appendix and Footer.

**Q2: What documentation standards apply to technical documentation?**
A: Technical documentation must use Markdown format, follow API specifications (OpenAPI/Swagger for APIs), include code examples, maintain accuracy, and follow the style guide. Architecture docs must include diagrams and clear component descriptions.

**Q3: Where should agent configurations be stored?**
A: Council agents: `.github/agents/council-agents/C##-name.agent.md`. Sync copies to `.windsurf/rules/` as needed. Organizational agents: `.github/agents/organizational-meta-agents/`. All agents must follow naming conventions.

**Q4: How often should documentation be reviewed?**
A: Critical documentation: Quarterly. Standard documentation: Semi-annually. Reference documentation: Annually. Agent configurations: Reviewed with each update.

### Knowledge Architecture

**Q5: What is the Stremiium knowledge taxonomy?**
A: Knowledge is organized by: Service (7 services), Council (16 councils), Type (Agent Configs, Technical, Product, Operational, Regulatory, Training), and Audience (Internal/External, Role-based).

**Q6: How is information classified at Stremiium?**
A: Five levels: Public (no restrictions), Internal (internal use only), Confidential (restricted access), Restricted (highly sensitive), Secret (board/executive only).

**Q7: What metadata is required for documents?**
A: Title, author, creation date, last updated date, version, classification, review date, owner, related documents.

**Q8: How do I find documentation?**
A: Use the central knowledge base with search, browse by taxonomy, check `.github/` for agent configs, `docs/` for product documentation, `task/` for project documentation.

### Agent Management

**Q9: How many agents does Stremiium have?**
A: 100+ agents across 16 councils: Tier 1 (C01-C10, ~45 agents), Tier 2 (C11-C13, ~10 agents), Tier 3 (C14-C16, ~13 agents), plus organizational and coordinator agents.

**Q10: Who can update agent configurations?**
A: Council Captains can update their agents. Chief-Librarian reviews for standards compliance. Major changes require Sparkling Curious notification.

**Q11: How are agent versions managed?**
A: Semantic versioning (Major.Minor.Patch). Major = structural changes, Minor = significant content updates, Patch = minor corrections. Version tracked in YAML front matter and change log.

**Q12: What is the TBS (Task Breakdown Structure)?**
A: Hierarchical task naming: T1 (major initiative), T1.1 (sub-task), T1.1.1 (granular step). Used for organizing all work with standardized folder structures.

### Compliance & Governance

**Q13: What is POPIA and how does it affect documentation?**
A: Protection of Personal Information Act (South Africa). Documentation must not contain unauthorized personal information. Data must be classified. Access controls required.

**Q14: How long must documentation be retained?**
A: Varies by type: Governance records (permanent), Regulatory docs (7+ years), Operational docs (2-5 years), Project docs (duration + 2 years). Specific retention schedules documented.

**Q15: Who is responsible for compliance documentation?**
A: Legal-Compliance Council creates content. Chief-Librarian ensures standards and organization. Compliance-Auditor verifies completeness.

**Q16: What happens if documentation is missing?**
A: Flagged in documentation audit. Risk assessment performed. Remediation plan created. Gap filled with priority based on risk.

### Tools & Systems

**Q17: What tools are used for knowledge management?**
A: Git/GitHub for version control, Confluence/Notion for wiki/knowledge base, Markdown for documentation, Slack/Teams for collaboration, specialized tools for specific domains.

**Q18: How do I request new documentation?**
A: Create KNO-T ticket in task/ folder following TBS protocol. Describe need, stakeholders, timeline. Knowledge Squad will assess and prioritize.

**Q19: How do I update existing documentation?**
A: Follow change control process. Minor updates: edit and publish with version bump. Major updates: draft, review, approve, then publish.

**Q20: What is the documentation review cycle?**
A: Quarterly for critical, semi-annual for standard, annual for reference. Automated reminders sent to document owners.

4. **Clear Ownership:** Every document has an owner
5. **Easy Access:** Minimize barriers to finding info
6. **Feedback Loop:** Continuous improvement

## 14.2 Common Pitfalls

### Pitfall 1: Documentation Drift

**Problem:** Documentation doesn't match reality
**Solution:** Regular reviews, update docs with code/system changes

### Pitfall 2: Information Silos

**Problem:** Knowledge trapped in teams
**Solution:** Cross-functional sharing, central repositories

### Pitfall 3: Over-Documentation

**Problem:** Too much documentation, hard to find what matters
**Solution:** Focus on user needs, clear organization, good search

### Pitfall 4: Outdated Templates

**Problem:** Templates don't reflect current standards
**Solution:** Regular template review, template version control
