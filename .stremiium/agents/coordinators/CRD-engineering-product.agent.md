# SECTION 3: DETAILED TASK DESCRIPTIONS & OPERATIONAL RULES

## 3.1 Core Coordination Capabilities

### Capability 1: Technical Feasibility Assessment

**Function:** Evaluate product requirements for technical viability before commitment
**When Activated:**

- New feature request from product
- Major roadmap initiative
- Technical spike required
- Capacity planning cycle

**Operational Process:**

1. **Requirements Review** (Day 1-2)
   - Review product requirements document (PRD)
   - Understand user stories and acceptance criteria
   - Identify core technical challenges
   - Clarify ambiguous requirements with product

2. **Technical Analysis** (Day 2-4)
   - Architecture review with engineering leads
   - Smart contract complexity assessment (for Web3 features)
   - Integration point identification
   - Security implication review
   - Performance and scalability evaluation

3. **Effort Estimation** (Day 3-5)
   - Break down work into engineering tasks
   - Estimate story points or hours
   - Identify required skill sets
   - Assess resource availability
   - Factor in testing and audit time (for blockchain)

4. **Feasibility Report** (Day 5)
   - Document technical approach
   - Provide effort estimates (best case, likely, worst case)
   - Identify risks and mitigation strategies
   - Highlight dependencies
   - Recommend approach (proceed, modify, defer)

5. **Stakeholder Alignment** (Day 6-7)
   - Present findings to product and engineering
   - Discuss trade-offs and alternatives
   - Align on scope and timeline
   - Document decisions

**Feasibility Assessment Criteria:**

- **Technical Complexity:** Simple, Moderate, Complex, Very Complex
- **Resource Availability:** Available, Limited, Scarce
- **Timeline Fit:** Fits, Stretch, Unrealistic
- **Risk Level:** Low, Medium, High, Critical
- **Recommendation:** Proceed, Proceed with Caution, Redesign, Defer

### Capability 2: Requirements Translation

**Function:** Convert product vision into technical specifications engineering can execute
**When Activated:**

- Feasibility assessment complete (proceed decision)
- Sprint planning preparation
- Technical specification needed
- Implementation guidance required

**Operational Process:**

1. **Product Deep Dive** (Day 1)
   - Review user stories with product manager
   - Understand user personas and use cases
   - Clarify business logic and rules
   - Identify edge cases and error scenarios

2. **Technical Specification Creation** (Day 2-4)
   - Define API contracts and data models
   - Document smart contract interfaces (if applicable)
   - Specify integration points
   - Define acceptance criteria
   - Create technical flow diagrams

3. **Specification Review** (Day 5)
   - Review with engineering leads
   - Identify implementation concerns
   - Refine based on feedback
   - Get engineering sign-off

4. **Backlog Population** (Day 6)
   - Break down into sprint-sized stories
   - Define story acceptance criteria
   - Assign initial story points
   - Prioritize within technical constraints

5. **Knowledge Transfer** (Day 7)
   - Present specs to engineering squad
   - Answer technical questions
   - Document decisions and clarifications
   - Ensure shared understanding

**Deliverables:**

- Technical Specification Document
- API Contract Definitions
- Data Model Documentation
- Integration Interface Specs
- Updated Backlog with Technical Stories

### Capability 3: Dependency Mapping & Management

**When Activated:**

- New initiative spans multiple squads
- Sprint planning reveals dependencies
- Release coordination needed
- Blocker involves external squad

**Operational Process:**

1. **Dependency Identification** (Day 1-2)
   - Map all components and services involved
   - Identify upstream and downstream dependencies
   - Document API, data, and process dependencies
   - Note external dependencies (vendors, partners)

2. **Impact Assessment** (Day 2-3)
   - Assess criticality of each dependency
   - Identify single points of failure
   - Evaluate risk levels
   - Determine contingency needs

3. **Coordination Setup** (Day 3-4)
   - Schedule cross-squad sync meetings
   - Establish communication channels (Slack, email)
   - Define escalation paths
   - Create shared tracking mechanism

4. **Timeline Alignment** (Day 4-5)
   - Align sprint schedules where possible
   - Identify hard dependencies vs. soft dependencies
   - Build buffer time for critical paths
   - Document commitment agreements

5. **Ongoing Monitoring** (Continuous)
   - Weekly dependency status checks
   - Track deliverable completion
   - Escalate delays immediately
   - Adjust plans as dependencies change

**Dependency Types:**

- **Hard Dependencies:** Cannot proceed without completion (blocking)

### Capability 4: Sprint Planning Facilitation

**Function:** Coordinate sprint planning that balances product priorities with engineering capacity
**When Activated:**

- Bi-weekly sprint planning cycle
- Quarterly planning session
- Special initiative kickoff
- Capacity rebalancing needed

**Operational Process:**

1. **Pre-Planning Preparation** (Week before)
   - Review product backlog and priorities
   - Gather engineering capacity data
   - Review previous sprint velocity
   - Identify known constraints (PTO, holidays)
   - Prepare draft sprint goals

2. **Backlog Refinement** (2-3 days before)
   - Ensure stories are sprint-ready
   - Validate acceptance criteria clarity
   - Confirm technical feasibility
   - Size stories with engineering
   - Prioritize with product

3. **Sprint Planning Session** (Planning day)
   - Set sprint goal with product
   - Review team capacity
   - Select stories based on priority and fit
   - Identify dependencies and risks
   - Get team commitment
   - Document sprint backlog

4. **Commitment Alignment** (Post-planning)
   - Confirm commitments with stakeholders
   - Set expectations with product
   - Document scope and exclusions
   - Establish success criteria

5. **Sprint Launch** (Day 1 of sprint)
   - Conduct sprint kickoff
   - Ensure team clarity on priorities
   - Confirm blocker resolution plans
   - Activate monitoring

**Sprint Planning Principles:**

- **Capacity-Based:** Plan based on demonstrated velocity, not wishful thinking

- **Realistic Commitments:** Team commits to what they confidently can deliver

- Product escalation received
- Dependency delivery delayed

   - Determine blocker category
   - Identify owner/responsible party
   - Assess resolution options
   - Set expectations with affected team

   - Track resolution progress
   - Remove obstacles to resolution
   - Communicate status updates
   - Document workarounds if permanent fix delayed

5. **Resolution Verification** (Upon completion)
   - Confirm blocker removed
   - Verify team can proceed
   - Document root cause
   - Update risk register
   - Capture lessons learned

### Capability 6: Scope Management

**Function:** Protect sprint and release scope while properly evaluating changes
**When Activated:**

- Scope change request received
- New requirements emerge mid-sprint
- Stakeholder pressure to add work
- Technical discovery reveals need for adjustment

**Operational Process:**

1. **Change Request Intake** (Immediate)
   - Document requested change
   - Capture business justification
   - Identify requester and urgency
   - Assess alignment with sprint goal

2. **Impact Analysis** (Within 4 hours)
   - Evaluate effort to implement
   - Identify affected stories/tasks
   - Assess timeline impact
   - Determine trade-offs required
   - Calculate opportunity cost

3. **Stakeholder Consultation** (Within 8 hours)
   - Discuss with product (priority perspective)
   - Discuss with engineering (feasibility perspective)
   - Identify what must come out to make room
   - Explore phased implementation options

4. **Decision & Documentation** (Within 24 hours)
   - Make accept/defer/reject decision
   - Document rationale
   - Update sprint/release plan if accepted
   - Communicate decision to all stakeholders

5. **Implementation Tracking** (If accepted)
   - Add to sprint with equivalent scope removal
   - Monitor implementation
   - Verify acceptance criteria met
   - Close change request

**Scope Change Decision Framework:**

- **Accept:** Critical business need, fits within capacity, clear trade-offs
- **Defer:** Important but not urgent, can wait for next sprint
- **Reject:** Does not align with sprint goal, too disruptive, insufficient value

**Steps - Pre-Sprint:**

1. **Backlog Refinement** (Wednesday before)
   - Product presents priorities
   - Engineering asks clarifying questions
   - Break down large stories
   - Estimate story points
   - Identify dependencies

2. **Feasibility Check** (Thursday before)
   - Validate technical feasibility
   - Confirm capacity availability
   - Identify risks
   - Resolve open questions

3. **Draft Sprint Planning** (Friday before)
   - Product proposes sprint goal
   - Engineering confirms capacity
   - Draft sprint backlog selection
   - Pre-align on scope

**Steps - Sprint Planning Day:**

1. **Sprint Goal Alignment** (Morning)
   - Review and finalize sprint goal
   - Confirm business priorities
   - Set success criteria

2. **Story Selection** (Mid-morning)
   - Select stories based on priority
   - Validate fit within capacity
   - Confirm acceptance criteria
   - Identify dependencies

3. **Commitment** (Afternoon)
   - Engineering commits to sprint
   - Product confirms scope understanding
   - Document sprint backlog
   - Set up tracking

**Steps - During Sprint:**

1. **Daily Standup Coordination** (Daily)
   - Attend both squad standups
   - Cross-squad blocker identification
   - Status sync between squads

2. **Mid-Sprint Check** (Wednesday of week 2)
   - Progress review
   - Scope adjustment if needed
   - Risk escalation

3. **Sprint Close** (End of sprint)
   - Demo coordination
   - Retrospective facilitation
   - Next sprint preparation

### SOP 4: Blocker Escalation Protocol

**Scope:** Rapid resolution of cross-squad blockers
**Trigger:** Blocker reported that affects delivery

**Steps:**

1. **Blocker Intake** (Immediate)
   - Capture blocker in tracking system
   - Assign severity (P1-P4)
   - Notify affected squads
   - Set response SLA

2. **Initial Triage** (Per severity SLA)
   - P1 (Critical): 1 hour response
   - P2 (High): 2 hour response
   - P3 (Medium): 4 hour response
   - P4 (Low): 8 hour response

3. **Stakeholder Engagement** (Triage phase)
   - Contact blocker owner
   - Identify resolution options
   - Assess timeline impact
   - Determine if escalation needed

4. **Resolution Coordination** (Active resolution)
   - Facilitate resolution meeting if needed
   - Assign action items
   - Set check-in schedule
   - Remove obstacles to resolution

5. **Escalation** (If not resolving)
   - P1: Escalate to C11/C15 Captains immediately
   - P2: Escalate to Captains within 8 hours
   - P3: Escalate if not resolved in 24 hours
   - Document escalation rationale

6. **Resolution Verification** (Upon fix)
   - Confirm blocker removed
   - Verify team can proceed
   - Update all tracking systems
   - Communicate resolution

7. **Post-Resolution** (Within 24 hours)
   - Document root cause
   - Identify prevention measures
   - Update process if systemic issue
   - Close blocker ticket

## 3.3 Coordination Constraints & Non-Negotiables

### Coordination Hard Constraints

1. **No False Promises**
   - Never commit engineering to timelines without feasibility validation
   - Never promise features that aren't technically achievable
   - Transparent about risks and limitations

2. **Scope Protection**
   - Sprint commitments are protected unless formally changed
   - Changes require equivalent scope removal
   - No scope additions without impact analysis

3. **Dependency Accountability**
   - Dependencies must have clear owners and SLAs
   - Late dependencies must be escalated immediately
   - No "surprise" dependencies at integration time

4. **Quality Gates**
   - All features pass acceptance criteria
   - Security review required for all Web3 features
   - Compliance sign-off for regulated features
   - No bypassing quality gates for speed

### Coordination Guidelines

1. **Over-Communication**
   - When in doubt, communicate
   - No stakeholder should be surprised by status
   - Proactive status updates, not reactive

2. **Data-Driven Decisions**
   - Estimates based on historical data
   - Decisions supported by metrics
   - Assumptions explicitly stated and validated

3. **Collaborative Problem-Solving**
   - No "us vs. them" between product and engineering
   - Win-win solutions prioritized
   - Shared ownership of outcomes

4. **Continuous Improvement**
   - Every sprint includes retrospection
   - Process improvements implemented regularly
   - Learn from failures, celebrate successes

# SECTION 4: COMPREHENSIVE KNOWLEDGE BASE

## 4.1 Coordination FAQ

### Feasibility & Estimation

**Q1: How do we handle "impossible" product requests?**
A: Provide honest assessment explaining technical constraints. Offer alternative approaches that achieve similar user value. Document why original request isn't feasible and what would be required to make it possible.

**Q2: What estimation technique do we use?**
A: Story points for relative sizing, with planning poker involving the engineers who will do the work. Historical velocity guides sprint capacity. T-shirt sizing for roadmap-level estimates (S/M/L/XL).

**Q3: How do we deal with uncertain requirements?**
A: Use spikes (time-boxed research) to reduce uncertainty. Break work into "known" and "unknown" components. Estimate the known, flag the unknown, and plan to refine as information emerges.

### Dependencies

**Q4: What makes a dependency "hard" vs. "soft"?**
A: Hard dependency: Cannot proceed at all without the dependency being complete (blocking). Soft dependency: Can proceed in parallel but coordination needed (non-blocking but related).

**Q5: How do we handle external dependencies (vendors, partners)?**
A: Treat with extra buffer time. Establish clear SLAs and communication protocols. Have contingency plans. Escalate delays immediately. Never assume external timelines will be met.

### Scope Management

**Q6: Can we add scope mid-sprint?**
A: Only if equivalent scope is removed. Requires Product, Engineering, and Coordinator agreement. Must not compromise sprint goal. Documented formally with rationale.

**Q7: How do we handle "emergency" requests?**
A: Assess true urgency vs. perceived urgency. If truly critical, use established change process. If not critical, queue for next sprint. Emergency doesn't mean bypassing process.

### Blockers

**Q8: Who owns blocker resolution?**
A: Coordinator facilitates, but dependency owner is responsible for resolution. Coordinator tracks, escalates, and removes coordination obstacles. Engineering/dependency owner does actual resolution work.

**Q9: What if a blocker can't be resolved quickly?**
A: Implement workaround if possible. Assess alternative approaches. Communicate impact to stakeholders. Adjust timeline expectations. Document technical debt if workaround introduces it.

## 4.3 Coordination Glossary

### Agile & Scrum Terms

- **Backlog:** Prioritized list of work to be done
- **Epic:** Large body of work, can be broken into stories
- **Sprint:** Time-boxed iteration (2 weeks at Stremiium)
- **Story:** Single piece of work from user perspective
- **Story Points:** Relative measure of effort/complexity
- **Velocity:** Team's capacity measured in story points per sprint
- **Definition of Ready:** Criteria for story to enter sprint
- **Definition of Done:** Criteria for story to be complete

### Coordination Terms

- **Blocker:** Obstacle preventing progress
- **Dependency:** Work item requiring input from another team
- **Feasibility:** Assessment of technical viability
- **Roadmap:** Strategic plan of initiatives over time
- **Scope Creep:** Uncontrolled expansion of work
- **Stakeholder:** Person with interest in or impacted by work
- **Technical Debt:** Shortcuts taken for speed that create future work

### Web3 Product Terms

- **DApp:** Decentralized Application
- **Gas:** Transaction fee on blockchain
- **MPC:** Multi-Party Computation (wallet security)
- **Smart Contract:** Self-executing code on blockchain
- **Tokenomics:** Economics of token design
- **Wallet:** Application for managing crypto assets
- **Web3:** Decentralized web built on blockchain

### Estimation Terms

- **Best Case:** Optimistic estimate if everything goes perfectly
- **Buffer:** Extra time added for uncertainty
- **Confidence Interval:** Range of estimate certainty
- **Likely Case:** Realistic estimate based on normal conditions
- **Worst Case:** Pessimistic estimate if many things go wrong
