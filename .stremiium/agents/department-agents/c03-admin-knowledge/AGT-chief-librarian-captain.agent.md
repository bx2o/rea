# SECTION 4: FIFTY+ FAQS, SKILLS & KNOWLEDGE LIBRARY

## 4.1 Knowledge Management & Documentation FAQs (28 FAQs)

**Q1: What should be included in a knowledge management system?**
A: Core components: (1) **Organizational information** (org chart, team info, contact info). (2) **Processes & procedures** (how we hire, how we release product, how we onboard customers). (3) **Policies** (code of conduct, confidentiality, IP, etc.). (4) **Decision records** (why did we choose technology X? what was the decision process?). (5) **Documentation** (product documentation, API docs, architecture docs). (6) **External resources** (customer success playbooks, sales materials). (7) **News & updates** (company news, team updates, important announcements). (8) **FAQs** (answers to common questions). Platforms: Wiki (Confluence, Notion), knowledge base (Zendesk, Help Scout), document management (SharePoint, Google Drive).

**Q2: What's the difference between a wiki and a knowledge base?**
A: **Wiki:** Internal collaborative documentation (all employees can create/edit). Examples: Confluence, Notion, GitBook. Benefits: Collaborative, fast updates, team-driven. Uses: Internal procedures, decision records, best practices. **Knowledge base:** Usually customer-facing (customers can view, but usually read-only). Examples: Zendesk, Help Scout, Intercom. Benefits: Organized for customer self-service, searchable. Uses: Product documentation, customer FAQs, how-tos. Many companies use both: Wiki for internal, KB for customer.

**Q3: How do you organize a knowledge management system?**
A: Structure: (1) **Start simple:** Top-level categories (operations, product, people, finance, etc.). (2) **Drill down:** Subcategories (hiring process under people; product release under product). (3) **Consistent structure:** All sections follow similar structure (makes predictable). (4) **Navigation:** Clear navigation (breadcrumbs, search, suggested links). (5) **Naming:** Clear, consistent naming (avoid jargon, use descriptive names). (6) **Tagging:** Add tags for discoverability (can find via search or tags). (7) **Owners:** Assign doc owner for each section (responsible for keeping current). (8) **Growth path:** Plan how to expand as organization grows. Example structure: Operations > Hiring > Recruiting Process > Interview Guide.

**Q4: What processes should be documented first (prioritization)?**
A: Priority order: (1) **High-impact, high-frequency:** Hiring, customer onboarding, product release (many do, easy to mess up if not documented). (2) **Compliance-critical:** Security incident response, data privacy procedures, financial controls (required for compliance). (3) **Difficult to learn:** Complex processes that take time to learn (IT systems, financial processes). (4) **Key person dependent:** Processes that only 1-2 people know (if they leave, process breaks). (5) **Error-prone:** Processes where mistakes happen often (leads and mistakes mean clear documentation needed). (6) **New processes:** Document immediately (easier to document while building than retrofit later). Start with top 20% of processes that drive 80% of value.

**Q5: How do you keep documentation current?**
A: Strategy: (1) **Review cadence:** Annual review of all docs (more frequently for critical docs). (2) **Owners:** Assign owner for each doc (they keep current). (3) **Version control:** Track who changed what, when (Git, version history). (4) **Feedback loop:** Employees report if doc is wrong/outdated. (5) **Trigger-based:** When process changes, update doc immediately (not waiting for annual review). (6) **Deprecated sections:** Mark outdated sections (so readers know not to follow). (7) **Archive old versions:** Keep old versions (for historical context). (8) **Maintenance effort:** Budget time/people for doc maintenance (often forgotten; docs decay). Rule: Documentation takes effort; budget for it.

**Q6: How do you document a complex process?**
A: Approach: (1) **Flowchart:** Visual representation (easier to understand than text). (2) **Step-by-step:** Number each step (clear sequence). (3) **Decision points:** If/then branches (decision criteria clear). (4) **Inputs/outputs:** What goes in? What comes out? (5) **Responsible parties:** Who does each step? (6) **Timeline:** How long each step takes? (7) **Exceptions:** What if X happens? (edge cases). (8) **Examples:** Real example of process (helps understanding). (9) **Links:** Links to related docs (context). (10) **Review:** Have process owner review (accuracy check). Tools: Flowchart tools (Lucidchart, Miro), Google Docs with embedded flowcharts, process mining tools.

**Q7: What's an architecture decision record (ADR) and why document it?**
A: ADR = document capturing architecture decision. Includes: (1) **Decision:** What decision did we make? (2) **Status:** Proposed, accepted, deprecated? (3) **Context:** Why this decision? What problem? What constraints? (4) **Options considered:** What alternatives? Why not those? (5) **Decision:** Why this option? (6) **Consequences:** What's impact? Tradeoffs? (7) **Related decisions:** How does this relate to other decisions? Example: "Use PostgreSQL for main database → Scalable, familiar, open-source, tradeoff: not NoSQL (more complex for some use cases)." Value: Future developers understand why decision was made (not "Why didn't we use MongoDB?").

**Q8: How do you capture lessons learned from incidents?**
A: Process: (1) **Postmortem meeting:** After incident, team meets (while fresh). (2) **Timeline:** What happened? When? (3) **Root cause:** Why did it happen? (true root cause, not symptom). (4) **Impact:** What happened? How many customers? Revenue loss? (5) **What went well:** What helped us respond? (6) **What didn't go well:** What slowed response? (7) **Action items:** What will we change? (8) **Documentation:** Postmortem published (so organization learns). Frequency: After every material incident (not after minor issues; wastes time). Value: Makes sure mistakes don't repeat.

**Q9: How do you involve employees in documentation?**
A: Approach: (1) **Assign owners:** Each process has owner (responsible for keeping current). (2) **Crowdsource:** Ask experts to document their knowledge (they know best). (3) **Templates:** Provide doc templates (lowers barrier to writing). (4) **Editing support:** Have technical writer help (improve clarity). (5) **Culture:** Value documentation (recognize people who document). (6) **Feedback:** Allow comments/suggestions (continuous improvement). (7) **Examples:** Show examples of good docs (sets standard). (8) **Training:** Quick training on how to use documentation system. Challenge: Employees busy; need to make documentation easy/rewarding.

**Q10: How do you handle documentation for remote teams?**
A: Extra importance: Remote teams must document more (can't pop next to someone ask question). Approach: (1) **Centralized system:** All docs in one place (accessible to all). (2) **Async communication:** Docs enable async (don't need synchronous meetings). (3) **Video:** For complex processes, consider short video (show instead of describe). (4) **FAQ:** Remote teams ask questions in writing (build FAQ from questions). (5) **Onboarding:** Longer onboarding doc (new hires get context remotely). (6) **Timezone-friendly:** Docs available 24/7 (can read when convenient). (7) **Communication:** Announce updates (email, Slack), since people won't overhear conversations. Challenge: Documentation critical for remote success; requires discipline.

**Q11: What's the right level of detail in documentation?**
A: Rule of thumb: **Enough so someone experienced in adjacent field can follow without asking.** Too little: Missing critical steps, reader gets stuck. Too much: Doc becomes overwhelming, nobody reads it. Balance: (1) **Target audience:** Who's reading? (new hire? experienced person in adjacent field?). (2) **Assumptions:** What can we assume they know? (2) **Complexity:** Match doc depth to task complexity. (4) **Examples:** Use examples liberally (easier to understand). (5) **Glossary:** Define jargon (don't assume knowledge). (6) **Navigation:** Clear structure so reader can skip read sections they know. Test: Have someone unfamiliar with process read doc and follow it.

**Q12: How do you make sure employees actually read/follow documentation?**
A: Approaches: (1) **Onboarding:** New employee onboarding includes reading core docs (training requirement). (2) **Access control:** Can't do task without reading doc (forced, but unpopular). (3) **Acknowledgment:** Employee signs they read/understand policy (legal requirement for policies). (4) **Culture:** Leadership models use/follow docs (if not used, employees won't). (5) **Integrations:** Link docs where people work (Slack, Google Docs, comments). (6) **Tests:** Quiz on critical docs (ensures understanding). (7) **Mistakes:** If employee makes preventable mistake, point to doc (reinforce value). Rule: Make docs easy to access/understand; cultural shift takes time.

**Q13: How do you handle documentation when tools/processes change frequently?**
A: Approach: (1) **Flexibility:** Design docs to be easy to update (not hardcoded values). (2) **Version control:** Use Git for docs (track changes, history). (3) **Living docs:** Expect docs to change; build in process for updates. (4) **Lower detail:** High-level procedures more stable; detailed steps change frequently. (5) **Links to specifics:** Link to external docs that change (avoid copying/duplicating). (6) **Deprecation:** Mark old sections (don't delete; keep for history). (7) **Change notification:** Alert team to doc changes (don't silently update). (8) **Priority:** Keep critical docs accurate; let lower-priority docs lag. Challenge: Too much change makes docs feel out-of-date; reduce change velocity if possible.

**Q14: What documentation tools should a company use?**
A: Options: (1) **Wiki (Confluence, Notion):** Collaborative internal docs. Best for internal procedures, decisions, best practices. Cost: $5-20/user. (2) **Knowledge base (Zendesk, Help Scout):** Customer-facing docs. Best for customer FAQs, product documentation. Cost: $30-300/month depending on features. (3) **Documentation sites (GitBook, ReadTheDocs):** Developer docs. Best for API, technical documentation. Cost: Free-$100+. (4) **Shared drives (Google Drive, SharePoint):** File-based storage. Less searchable, but familiar. Cost: Usually included in G Suite/Office 365. (5) **Combination:** Use multiple tools for different purposes. Recommendation: Start with one tool; expand later.
