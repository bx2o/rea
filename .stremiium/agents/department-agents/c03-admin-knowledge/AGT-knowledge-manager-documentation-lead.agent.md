# SECTION 4: FIFTY+ FAQS, SKILLS & KNOWLEDGE LIBRARY

## 4.1 Fifty+ Frequently Asked Questions (FAQs)

### **Category 1: KNOWLEDGE MANAGEMENT STRATEGY (14 FAQs)**

**Q1: What's the difference between a knowledge base, wiki, and documentation?**
A: **Knowledge base:** Searchable repository of articles/FAQs addressing common questions. Tool: Zendesk, Confluence, Slite. Example: Customer product FAQ. **Wiki:** Collaborative documentation edited by community. Tool: Confluence, MediaWiki. Example: Company policies, procedures. **Documentation:** Technical reference (software, APIs). Tool: ReadTheDocs, GitBook. Example: API documentation. **Choice:** Start with wiki for internal knowledge; later add searchable knowledge base.

**Q2: What content should be in a knowledge repository?**
A: Core categories: (1) **Onboarding:** New employee handbook, role guides, first-day checklist. (2) **Policies:** Company policies (code of conduct, time off, benefits, etc.). (3) **Procedures:** How-to guides (expense reporting, hiring, procurement, etc.). (4) **Product:** Product documentation, features, FAQs. (5) **Processes:** Business processes (meeting request, approval workflows, etc.). (6) **Teams:** Team pages (who's on teams, what do they do, how to contact?). (7) **Tools:** How to use company tools (Slack, GitHub, etc.). (8) **Meeting notes:** Archive of decision meetings (why was decision made?). (9) **Reference:** Company information (org chart, calendar, office locations). Prioritize: Start with onboarding + common processes; expand over time.

**Q3: How do you keep documentation current?**
A: Process: (1) **Ownership:** Assign owner to each doc (who maintains?). (2) **Review frequency:** Doc type matters (policies: annually; procedures: quarterly; FAQs: ongoing). (3) **Automation:** Reminders (email owner "please review/update"). (4) **Versioning:** Track who changed what (some platforms do this automatically). (5) **Feedback loop:** Users suggest edits (comment system helps). (6) **Audit:** Periodically scan all docs (is this still accurate?). (7) **Archive:** Move outdated docs to archive (don't delete; might be useful for history). Effort: ~5-10% of team time to maintain. Technology: Confluence, Notion make this easier.

**Q4: How do you move documentation from scattered (Docs, Slack, email) to centralized?**
A: Approach: (1) **Inventory:** What docs exist? Where? (2) **Deduplication:** Same topic documented multiple places? Consolidate. (3) **Assessment:** Which docs important? Keep/discard. (4) **Migration:** Move to new system. (5) **Cleanup:** Organize, use consistent format. (6) **Redirect:** Old locations → links to new location. (7) **Train:** Teach employees new location. Effort: 2-4 weeks for initial migration. Don't try to perfect all docs at once; get them moved, then improve iteratively.

**Q5: What's a good information architecture for company wiki?**
A: Structure option 1 (by function): Engineering, Finance, People, Operations, Marketing (teams navigate by their area). Structure option 2 (by use case): Onboarding, Policies, Processes, Reference (users navigate by what they need). Structure option 3 (hybrid): Top-level by use case (Onboarding); sub-sections by function (Onboarding → Engineering onboarding, Finance onboarding). Recommendation: Hybrid for most companies. Test with users (can they find what they need?). Iterate.

**Q6: How do you decide what to put in video vs. written documentation?**
A: **Video:** Use for: Software tutorials (showing where to click), onboarding (warmth, engagement), complex procedures (hard to describe in text). Cost: More effort to create/maintain. **Text:** Use for: Reference docs (people skim/search), policies (legal precision), detailed explanations. Cost: Easier to create/maintain. Recommendation: Combination; video + text transcript (covers both learning styles). Example: Procuring spending > $5K has written policy + video walkthrough.

**Q7: How do you handle documentation in technical teams (code documentation)?**
A: Approach: (1) **In-code comments:** Explain why (not what—code shows what). (2) **API documentation:** Generated from code (tool: Swagger, OpenAPI). (3) **Architecture documentation:** System design, decisions. (4) **Runbook:** How to operate system (deploy, monitor, debug, incident response). (5) **Onboarding for engineers:** Setup environment, first commit, team norms. (6) **Library/modules:** What each module does, how to use. Tools: ReadTheDocs, GitBook, GitHub wiki. Assign ownership: Engineers maintain technical docs, not separate team.

**Q8: What's a good tagging/labeling strategy for documentation?**
A: Tags help users find docs. Examples: (1) **Audience:** "new-hire," "manager," "engineer," "customer." (2) **Topic:** "process," "policy," "tutorial," "reference." (3) **Function:** "finance," "hiring," "product," "sales." (4) **Priority:** "essential," "frequently-asked," "advanced." (5) **Status:** "current," "deprecated," "draft." Use consistent tags across all docs. Don't over-tag (3-5 tags per doc). Tools: Most wiki platforms support tags. Maintain tag list (don't let hundreds of tags proliferate).

**Q9: How do you measure knowledge base effectiveness?**
A: Metrics: (1) **Search analytics:** What are users searching for? Are results relevant? (2) **Documentation ratings:** Docs have thumbs-up/down; track positive ratings. (3) **Time to answer:** Track if doc available, time to answer drops. (4) **Employee feedback:** Survey on documentation usefulness. (5) **Onboarding impact:** Does onboarding documentation reduce time to productivity? (6) **Question volume:** Are repeated questions declining? (7) **Usage:** Who accesses docs? How often? Tools: Most wiki platforms have analytics. Analyze quarterly.

**Q10: How do you write clear, accessible documentation?**
A: Tips: (1) **Use plain language:** Avoid jargon; if necessary, define. (2) **Active voice:** "Click the button" not "the button should be clicked." (3) **Short paragraphs:** Break up long paragraphs. (4) **Headings:** Use headings to organize. (5) **Examples:** Include examples (much clearer than abstract description). (6) **Visual aids:** Screenshots, diagrams help. (7) **Concise:** Get to point fast (busy employees). (8) **Consistent format:** Same structure for similar docs. Test with non-expert (can they understand?).

**Q11: What's the best documentation platform/tool?**
A: Options: (1) **Confluence:** Popular, integrates with Jira, good for teams. Cost: ~$5-10/user/month. (2) **Notion:** Very flexible, modern, free-ish. Cost: Free for small teams, $10/month for feature access. (3) **GitHub Wiki:** Free if code on GitHub. Simple but basic. (4) **Slite:** Chat-first knowledge, modern UX. Cost: ~$10/user/month. (5) **Zendesk/Helpscout:** Knowledge base + customer support. Cost: $100+/month. Choice: For internal: Confluence or Notion. For customer-facing: Zendesk. Start simple; upgrade if needed.

**Q12: How do you get subject matter experts (SMEs) to document their knowledge?**
A: Challenge: SMEs busy; documentation feels like overhead. Approach: (1) **Make it easy:** Provide templates, guides. (2) **Support:** Have documentation person interview SME, draft doc for review (SME reviews, not writes from scratch). (3) **Time:** Block calendar time (not "whenever you have time"). (4) **Incentives:** Recognition (people appreciate being asked). (5) **Iteration:** First draft doesn't need perfect; improve over time. (6) **Ownership:** SME owns their docs; updates fall to them. (7) **Recognition:** Thank SMEs; highlight their expertise. Effort: 2-4 hours per SME to document their domain.

**Q13: What's a documentation audit and how often?**
A: Audit: Review all documentation for accuracy, completeness, organization. Steps: (1) **List all docs.** (2) **Assign me to each.** (3) **Review:** Is it accurate? Current? Well-organized? (4) **Feedback:** What needs update? (5) **Plan:** Create list of improvements. (6) **Execute:** Update docs. Frequency: Annual or semi-annual (depending on rate of change). Effort: 40-80 hours for typical company. Value: Ensures docs don't become stale.

**Q14: How do you handle documentation for remote/distributed teams?**
A: Importance: Higher importance (can't just ask colleague). Considerations: (1) **Time zones:** Make sure docs available 24/7 (not "ask person during US business hours"). (2) **Async:** Docs support async work (don't require real-time communication). (3) **Completeness:** Remote teams need more explicit documentation (can't observe/overhear). (4) **Examples:** Lots of examples (clarify expected behavior). (5) **Video:** Video helpful (shows interaction/tone). (6) **Feedback:** Easy way to report docs unclear (chat channel for feedback). Effort: More extensive than co-located.
