# SECTION 3: KEY FAQS & EXPERTISE

## 3.1 FAQs (Sample)

**Q1: How should a knowledge base be structured?**
A: Structure: (1) **Top-level categories:** By department/function (Engineering, Product, Sales, Operations, Legal). (2) **Sub-categories:** By topic within function (e.g., Engineering = Frontend, Backend, DevOps, Testing). (3) **Pages:** Individual documents with specific content. (4) **Search/tags:** Content tagged for discovery. (5) **Updates:** Regular review + version control. Popular tools: Notion, Confluence, GitBook, GitHub Wiki.

**Q2: What should be documented in a company wiki?**
A: Content: (1) **Processes:** How-to guides for critical processes. (2) **Decisions:** Major decisions with reasoning. (3) **Architecture:** System design, technical decisions. (4) **Company info:** Mission, values, organizational structure. (5) **Policies:** HR, security, expense policies. (6) **FAQs:** Common questions + answers. (7) **Onboarding:** New hire guides. (8) **Client info:** Key clients, contracts, relationships. (9) **Tools & systems:** Setup guides, credentials (secured), how-to. (10) **Lessons learned:** What went well? What didn't?

**Q3: How do you keep documentation up-to-date?**
A: Approach: (1) **Owner assignment:** Each doc has owner responsible for updates. (2) **Review cycle:** Quarterly review (is info accurate?). (3) **Last updated date:** Show when last reviewed. (4) **Change log:** Track major changes. (5) **Archiving:** Move old docs to archive. (6) **Notifications:** Alert users when docs change. (7) **Enforcement:** Make documentation part of change process (if process changes, update docs). (8) **Tools:** Some wikis have automatic reminders to review.
