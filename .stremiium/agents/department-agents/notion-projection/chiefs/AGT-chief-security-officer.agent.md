# SECTION 4: KEY FAQS & KNOWLEDGE LIBRARY

## 4.1 Thirty+ Frequently Asked Questions

### Category 1: SECURITY STRATEGY (6 FAQs)

**Q1: What is a security strategy?**
A: Security strategy aligns security with business: (1) **Risk-Based:** Focus on highest risks. (2) **Layered:** Defense in depth. (3) **Proactive:** Threat-informed. (4) **Business-Enabling:** Support innovation. (5) **Continuous:** Always improving. Components: Risk assessment, control framework, metrics, roadmap.

**Q2: How do you balance security and business agility?**
A: Balance approaches: (1) **Risk-Based:** Not everything needs maximum security. (2) **Automated:** Security at speed of DevOps. (3) **Self-Service:** Empower teams with guardrails. (4) **Shift-Left:** Security early in lifecycle. (5) **Champions:** Embed security in teams. Principle: "Secure by default, exceptional access with approval."

**Q3: What is defense in depth?**
A: Defense in depth: Multiple security layers so if one fails, others protect. Layers: (1) **Perimeter:** Firewalls, WAF. (2) **Network:** Segmentation, IDS. (3) **Endpoint:** EDR, antivirus. (4) **Application:** Secure code, input validation. (5) **Data:** Encryption, access controls. (6) **Identity:** MFA, least privilege. (7) **Monitoring:** Detection and response.

**Q4: How do you build a security roadmap?**
A: Roadmap development: (1) **Current State:** Assess maturity. (2) **Target State:** Define goals. (3) **Gaps:** Identify what needs fixing. (4) **Priorities:** Risk-based ranking. (5) **Quick Wins:** Fast value. (6) **Foundations:** Build basics first. (7) **Investments:** Major initiatives. Timeframe: 12-24 months, quarterly reviews.

**Q5: What is threat-informed defense?**
A: Threat-informed defense: Base security on actual adversary behaviors. Sources: (1) **Threat Intelligence:** IOCs, TTPs. (2) **ATT&CK Framework:** Known techniques. (3) **Industry Reports:** Sector-specific threats. (4) **Intelligence Sharing:** ISACs, partners. (5) **Internal Data:** Your incidents. Application: Test defenses against likely threats.

**Q6: How do you measure security posture?**
A: Security metrics: (1) **Operational:** MTTD, MTTR, alerts. (2) **Vulnerability:** Patch time, coverage. (3) **Compliance:** Audit scores, gaps. (4) **Behavioral:** Training, phishing tests. (5) **Maturity:** Framework levels. (6) **Risk:** Critical asset protection. (7) **Business:** Security incidents, downtime. Dashboard: Balanced view, trends over time.

### Category 2: THREAT & INCIDENT RESPONSE (6 FAQs)

**Q7: What is a security incident?**
A: Security incident: Event that compromises confidentiality, integrity, or availability. Types: Malware, phishing, data breach, DDoS, insider threat, physical breach. Severity: SEV1 (critical), SEV2 (high), SEV3 (medium), SEV4 (low). All confirmed incidents require response.

**Q8: How do you build an incident response plan?**
A: IR plan components: (1) **Preparation:** Tools, contacts, procedures. (2) **Identification:** Detection and declaration. (3) **Containment:** Stop spread. (4) **Eradication:** Remove threat. (5) **Recovery:** Restore systems. (6) **Lessons Learned:** Post-incident review. (7) **Communication:** Internal and external. Testing: Tabletop exercises, simulations.

**Q9: What is threat hunting?**
A: Threat hunting: Proactive search for threats that evade detection. Process: (1) **Hypothesis:** Based on intel or anomalies. (2) **Data Collection:** Logs, network, endpoints. (3) **Analysis:** Pattern recognition. (4) **Investigation:** Deep dive on findings. (5) **Response:** If threat found. Tools: SIEM, EDR, network analysis. Skill: Analytical thinking, adversary knowledge.

**Q10: What is a SIEM and how does it work?**
A: SIEM (Security Information and Event Management): Collects, correlates, and analyzes security logs. Functions: (1) **Collection:** Centralized logging. (2) **Correlation:** Connect events across sources. (3) **Detection:** Rules and ML identify threats. (4) **Alerting:** Notify analysts. (5) **Investigation:** Tools for analysis. (6) **Reporting:** Compliance and metrics. Tools: Splunk, Sentinel, QRadar, Chronicle.

**Q11: How do you conduct a forensic investigation?**
A: Forensic process: (1) **Identification:** Scope and systems. (2) **Preservation:** Forensic copies, chain of custody. (3) **Collection:** Evidence gathering. (4) **Examination:** Analysis of artifacts. (5) **Analysis:** Timeline, attribution. (6) **Reporting:** Findings and recommendations. Principles: Integrity, objectivity, chain of custody, documentation.

**Q12: What is the difference between incident response and disaster recovery?**
A: **Incident Response:** Security event (breach, malware). Focus: Contain, eradicate, recover. **Disaster Recovery:** Infrastructure failure (outage, natural disaster). Focus: Business continuity, system recovery. Overlap: Major incidents may trigger DR. Integration: Coordinated plans.

### Category 3: COMPLIANCE & GOVERNANCE (6 FAQs)

**Q13: What is the difference between compliance and security?**
A: **Compliance:** Meeting regulatory/standard requirements. Box-checking, documentation, audit-focused. **Security:** Actual protection of assets. Risk-based, threat-focused, operational. Relationship: Compliance is minimum baseline, security is goal. Gap: Can be compliant but not secure (checkbox security). Aim: Security enables compliance.

**Q14: What is SOC 2 and how do you achieve it?**
A: SOC 2: Audit of security controls (Trust Services Criteria). Types: Type 1 (design), Type 2 (operating effectiveness). Criteria: Security, Availability, Processing Integrity, Confidentiality, Privacy. Process: (1) Gap assessment. (2) Remediation. (3) Audit (external). (4) Report. Maintenance: Annual audits. Value: Customer trust, competitive advantage.

**Q15: What is the NIST Cybersecurity Framework?**
A: NIST CSF: Voluntary guidance for managing cybersecurity risk. Functions: (1) **Identify:** Asset management, risk assessment. (2) **Protect:** Access control, awareness, data security. (3) **Detect:** Anomalies, continuous monitoring. (4) **Respond:** Response planning, communications. (5) **Recover:** Recovery planning, improvements. Tiers: Partial, Risk Informed, Repeatable, Adaptive.

**Q16: How do you handle vendor security assessments?**
A: Vendor assessment: (1) **Classify:** Risk tier (high/medium/low). (2) **Questionnaire:** Security practices. (3) **Evidence:** Documentation, certifications. (4) **Review:** Against requirements. (5) **Risk Acceptance:** Gap remediation or acceptance. (6) **Contract:** Security clauses. (7) **Monitor:** Ongoing oversight. Automation: Use tools like Vanta, OneTrust, or SecurityScorecard.

**Q17: What is a security policy?**
A: Security policy: Management intent for security. Hierarchy: (1) **Policy:** High-level statements. (2) **Standards:** Mandatory requirements. (3) **Procedures:** Step-by-step instructions. (4) **Guidelines:** Recommended practices. Development: Risk-based, stakeholder input, management approval, training, enforcement. Review: Annual or when significant change.

**Q18: What are security controls?**
A: Security controls: Safeguards to reduce risk. Types: (1) **Preventive:** Stop incident (firewall, MFA). (2) **Detective:** Identify incident (SIEM, logs). (3) **Corrective:** Fix after incident (backup, patching). (4) **Deterrent:** Discourage attack (warning banners). (5) **Compensating:** Alternative when primary not possible. Frameworks: NIST 800-53, ISO 27002.

### Category 4: TECHNICAL SECURITY (6 FAQs)

**Q19: What is zero trust architecture?**
A: Zero Trust: "Never trust, always verify." Principles: (1) **Verify explicitly:** Authenticate and authorize every access. (2) **Least privilege:** Minimum access needed. (3) **Assume breach:** Micro-segmentation limits blast radius. Implementation: Identity-centric, micro-segmentation, continuous validation, data-centric security. Contrast: Replaces perimeter-based "trust but verify."

**Q20: How do you secure cloud environments?**
A: Cloud security: (1) **Shared Responsibility:** Know who does what. (2) **IAM:** Strong identity, least privilege. (3) **Data:** Encryption, classification. (4) **Network:** VPCs, security groups. (5) **Monitoring:** CloudTrail, Flow Logs. (6) **Config:** Security benchmarks (CIS). (7) **CASB:** Cloud access security broker. Model: Shift from perimeter to identity and data-centric.

**Q21: What is the difference between encryption at rest and in transit?**
A: **At Rest:** Data stored encrypted (disk, database). Protects from physical theft, backup exposure. **In Transit:** Data moving encrypted (TLS, VPN). Protects from interception. Both needed for complete protection. Standards: AES-256 for at rest, TLS 1.3 for in transit. Key management: Critical—secure generation, storage, rotation.

**Q22: What is multi-factor authentication (MFA)?**
A: MFA: Multiple verification methods. Factors: (1) **Knowledge:** Password, PIN. (2) **Possession:** Phone, token. (3) **Inherence:** Fingerprint, face. Types: SMS (weak), TOTP (better), FIDO2/WebAuthn (strongest). Implementation: Enforce for all users, privileged accounts first. Backup: Recovery codes for lockout. Resistance: Push adoption, provide support.

**Q23: What is a Web Application Firewall (WAF)?**
A: WAF: Filters and monitors HTTP traffic. Protection: SQL injection, XSS, CSRF, DDoS. Deployment: Cloud (AWS WAF, Cloudflare), on-premise. Rules: OWASP Core Rule Set, custom. Limitation: Not silver bullet, signature-based may miss zero-days. Complement: Secure code, input validation, patching.

**Q24: What is penetration testing?**
A: Penetration testing: Simulated attack to find vulnerabilities. Types: (1) **Black Box:** No knowledge. (2) **White Box:** Full knowledge. (3) **Gray Box:** Partial knowledge. Scopes: Network, web app, mobile, social engineering. Frequency: Annual minimum, after major changes, continuous with bug bounty. Value: Find what scanners miss, test detective controls, prioritize fixes.

### Category 5: AWARENESS & CULTURE (6 FAQs)

**Q25: How do you build a security culture?**
A: Security culture: (1) **Leadership:** Executives model and prioritize. (2) **Responsibility:** Everyone's job, not just security team. (3) **Education:** Regular training, relevant to role. (4) **Communication:** Transparent about threats. (5) **Positive:** "Thank you for reporting" not punishment. (6) **Integration:** Security in processes. (7) **Metrics:** Measure and improve.

**Q26: What is security awareness training?**
A: Security awareness: Education on threats and best practices. Content: Phishing, password hygiene, social engineering, data handling, incident reporting. Methods: Online modules, simulations, workshops, newsletters. Frequency: Onboarding, annual refresh, triggered (after incident). Measurement: Quiz scores, phishing test results, incident reports.

**Q27: How do you run a phishing simulation?**
A: Phishing simulation: (1) **Plan:** Scope, timing, scenarios. (2) **Create:** Realistic but safe emails. (3) **Send:** To targeted users. (4) **Track:** Who clicks, who reports. (5) **Educate:** Immediate training for clickers. (6) **Analyze:** Trends and patterns. (7) **Report:** Aggregate metrics, no blame. Goal: Behavior change, not entrapment. Frequency: Monthly or quarterly.

**Q28: What is a security champion program?**
A: Security champions: Embedded security advocates in teams. Role: (1) **Bridge:** Between security and dev/ops. (2) **Advisor:** First line security questions. (3) **Promoter:** Security initiatives. (4) **Feedback:** Team needs to security. Selection: Volunteers, respected team members. Support: Training, tools, access, recognition. Value: Scale security, build culture.

**Q29: How do you handle security fatigue?**
A: Security fatigue: Users overwhelmed by security requirements. Signs: Password reuse, MFA complaints, ignoring alerts. Mitigation: (1) **Reduce Friction:** SSO, seamless MFA. (2) **Prioritize:** Focus on high-risk. (3) **Automate:** Behind-the-scenes security. (4) **Contextual:** Risk-based, not blanket. (5) **Educate:** Explain why. (6) **Listen:** User feedback. Balance: Security vs. usability.

**Q30: How do you report security to the board?**
A: Board reporting: (1) **Executive Summary:** Key messages. (2) **Risk:** Current risk posture, trends. (3) **Incidents:** Significant events, lessons. (4) **Metrics:** KPIs over time. (5) **Initiatives:** Major projects, status. (6) **Investment:** Budget needs, ROI. (7) **Threats:** Relevant landscape. Format: Visual, concise, business language. Cadence: Quarterly.

# SECTION 5: SOPs & STANDARD OPERATING PROCEDURES

## SOP 1: Security Incident Response

**Duration:** Variable | **Frequency:** As needed | **Owner:** Security Operations

1. **Detect:** Alert or report received
2. **Triage:** Severity assessment
3. **Declare:** Incident commander assigned
4. **Contain:** Limit damage
5. **Eradicate:** Remove threat
6. **Recover:** Restore operations
7. **Post-Incident:** Lessons learned
8. **Report:** Documentation and communication
9. **Follow-up:** Long-term fixes

**Severity Levels:**

- SEV1: Critical (data breach, ransomware)
- SEV2: High (malware, unauthorized access)
- SEV3: Medium (policy violation, suspicious activity)
- SEV4: Low (inquiry, false positive)

## SOP 2: Vulnerability Management

**Duration:** Ongoing | **Frequency:** Continuous | **Owner:** Vulnerability Management Team

1. **Discover:** Scan and identify vulnerabilities
2. **Assess:** Risk scoring (CVSS + context)
3. **Prioritize:** Based on risk and asset criticality
4. **Assign:** Owner and timeline
5. **Remediate:** Patch or mitigate
6. **Verify:** Confirm fix
7. **Report:** Metrics and status
8. **Exception:** Document accepted risk

**SLAs:**

- Critical: 7 days
- High: 30 days
- Medium: 90 days
- Low: 180 days

## SOP 3: Security Review

**Duration:** 1-5 days | **Frequency:** Per project | **Owner:** Security Architect

1. **Request:** Project team submits
2. **Scope:** Define review boundaries
3. **Threat Model:** Identify risks
4. **Review:** Architecture, code, config
5. **Findings:** Document issues
6. **Recommendations:** Risk-based solutions
7. **Remediate:** Project addresses
8. **Validate:** Security confirms
9. **Approve:** Sign-off
10. **Track:** Monitor residual risk

**Fast Track:**

- Standard patterns
- Low-risk changes
- Pre-approved architectures
