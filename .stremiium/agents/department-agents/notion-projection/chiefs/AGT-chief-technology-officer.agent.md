# SECTION 4: KEY FAQS & KNOWLEDGE LIBRARY

## 4.1 Fifty+ Frequently Asked Questions

### Category 1: ARCHITECTURE PRINCIPLES & PATTERNS (10 FAQs)

**Q1: What makes a good software architecture?**
A: Good architecture exhibits: (1) **Scalability:** Handles growth without redesign. (2) **Reliability:** Resilient to failures. (3) **Maintainability:** Easy to understand and modify. (4) **Security:** Protected by design. (5) **Performance:** Meets latency and throughput needs. (6) **Simplicity:** As simple as possible (but no simpler). (7) **Flexibility:** Adaptable to changing requirements. (8) **Observability:** Understand system behavior. Trade-offs: Balance these based on business priorities.

**Q2: What's the difference between monolithic and microservices architecture?**
A: **Monolithic:** Single deployable unit. Pros: Simpler development, easier testing, better performance (no network calls). Cons: Harder to scale independently, technology lock-in, longer deploy cycles. **Microservices:** Independent deployable services. Pros: Scalable independently, technology diversity, team autonomy, resilience. Cons: Distributed system complexity, network latency, data consistency challenges, operational overhead. Choose: Monolith for early-stage/simple domains; microservices for scale/complex domains.

**Q3: How do you decide between synchronous and asynchronous communication?**
A: **Synchronous (REST/gRPC):** Use when immediate response needed, strong consistency required, simple request/response patterns. **Asynchronous (events/message queues):** Use for decoupling, handling high throughput, long-running operations, eventual consistency acceptable. Hybrid: Most systems use both. Pattern: Command (sync) vs. Event (async).

**Q4: What is domain-driven design (DDD)?**
A: DDD aligns software design with business domains: (1) **Bounded Context:** Clear boundaries where domain model applies. (2) **Entities:** Objects with identity. (3) **Value Objects:** Immutable objects without identity. (4) **Aggregates:** Consistency boundaries. (5) **Domain Events:** Capture business occurrences. (6) **Repositories:** Persistence abstraction. Benefit: Business and technology aligned on language and structure.

**Q5: How do you handle data consistency in distributed systems?**
A: Consistency patterns: (1) **Strong Consistency:** All nodes see same data (sacrifices availability). (2) **Eventual Consistency:** Temporary inconsistency resolves (sacrifices immediate consistency). (3) **Saga Pattern:** Distributed transactions via compensating actions. (4) **CQRS:** Separate read and write models. (5) **Event Sourcing:** State derived from event log. Choose: Based on business requirements, not technical preference.

**Q6: What is API-first design?**
A: API-first means designing APIs before implementation: (1) **Contract:** API specification is the contract. (2) **Parallel Development:** Frontend and backend can develop against spec. (3) **Documentation:** Spec serves as documentation. (4) **Testing:** Mock servers for testing. Tools: OpenAPI, GraphQL schemas. Process: Design → Review → Implement → Test.

**Q7: How do you approach system decomposition?**
A: Decomposition strategies: (1) **By Business Capability:** Align services to business functions. (2) **By Domain:** Bounded contexts from DDD. (3) **By Team:** Conway's Law - architecture follows organization. (4) **By Change Frequency:** Separate stable from rapidly changing. (5) **By Scale:** Separate high-scale from low-scale. Anti-pattern: Decompose by technical layer (all DBs together).

**Q8: What are the fallacies of distributed computing?**
A: Eight fallacies: (1) Network is reliable. (2) Latency is zero. (3) Bandwidth is infinite. (4) Network is secure. (5) Topology doesn't change. (6) There is one administrator. (7) Transport cost is zero. (8) Network is homogeneous. Reality: Plan for network failures, latency, and security. Design for failure.

**Q9: How do you manage technical debt?**
A: Technical debt management: (1) **Track:** Document known debt. (2) **Measure:** Quantify impact (velocity drag, bugs, maintenance). (3) **Prioritize:** Fix high-impact debt first. (4) **Allocate:** Reserve capacity (10-20%) for debt paydown. (5) **Prevent:** Code reviews, architecture reviews, testing. (6) **Strategic:** Some debt is acceptable for speed. Rule: Intentional, tracked debt is acceptable; unknown, uncontrolled debt is dangerous.

**Q10: What is the C4 model for architecture documentation?**
A: C4 model levels: (1) **Context:** System in environment (users, external systems). (2) **Container:** Applications/services and data stores. (3) **Component:** Components within containers. (4) **Code:** Actual implementation (optional). Use: Context for executives, Container for architects, Component for developers. Tool: Diagrams as code (PlantUML, Mermaid, Structurizr).

### Category 2: CLOUD & INFRASTRUCTURE (10 FAQs)

**Q11: How do you choose between cloud providers?**
A: Evaluation criteria: (1) **Services:** Do they offer services you need? (2) **Pricing:** Total cost of ownership. (3) **Performance:** Latency to your users. (4) **Compliance:** Certifications you need. (5) **Ecosystem:** Integration with your stack. (6) **Support:** Enterprise support quality. (7) **Lock-in:** Proprietary vs. portable services. (8) **Team:** Existing skills and experience. Strategy: Multi-cloud for resilience, but master one first.

**Q12: What's the difference between containers and serverless?**
A: **Containers (Docker/Kubernetes):** Package apps with dependencies. Pros: Consistent environments, portable, granular control. Cons: Operational complexity, need orchestration. **Serverless (Functions):** Run code without managing servers. Pros: No infrastructure management, auto-scale, pay-per-use. Cons: Cold starts, limited execution time, vendor lock-in. Hybrid: Many use both - containers for long-running, complex apps; serverless for event-driven, variable workloads.

**Q13: How do you design for high availability?**
A: High availability patterns: (1) **Redundancy:** Multiple instances across AZs/regions. (2) **Failover:** Automatic detection and recovery. (3) **Load Balancing:** Distribute traffic. (4) **Health Checks:** Remove unhealthy instances. (5) **Circuit Breakers:** Fail fast when dependencies down. (6) **Graceful Degradation:** Partial functionality during issues. Target: 99.9% ("three nines") = 8.76 hours downtime/year.

**Q14: What is Infrastructure as Code (IaC)?**
A: IaC manages infrastructure through code: (1) **Declarative:** Define desired state (Terraform, CloudFormation). (2) **Imperative:** Define steps to reach state (Ansible, scripts). Benefits: Version control, reproducibility, peer review, automation. Practices: GitOps, immutable infrastructure, state management, modular design. Avoid: Manual changes that drift from code.

**Q15: How do you approach multi-region architecture?**
A: Multi-region strategies: (1) **Active-Passive:** Primary region, standby for disaster recovery. (2) **Active-Active:** Traffic split across regions. (3) **Partitioned:** Different data/user sets per region. Challenges: Data replication latency, split-brain scenarios, cost. Use when: Compliance requirements, disaster recovery needs, performance to global users.

**Q16: What's the role of a service mesh?**
A: Service mesh (Istio, Linkerd) provides: (1) **Service Discovery:** Find services dynamically. (2) **Load Balancing:** Intelligent traffic distribution. (3) **mTLS:** Automatic service-to-service encryption. (4) **Observability:** Distributed tracing, metrics. (5) **Traffic Management:** Canary, A/B testing, circuit breaking. Trade-off: Adds complexity and latency. Use when: Many microservices, complex traffic management needs.

**Q17: How do you optimize cloud costs?**
A: Cost optimization: (1) **Right-sizing:** Match resources to actual usage. (2) **Reserved Instances:** Commit for predictable workloads. (3) **Spot/Preemptible:** Use for fault-tolerant workloads. (4) **Auto-scaling:** Scale down when demand low. (5) **Storage Tiers:** Move infrequent data to cheaper storage. (6) **Monitoring:** Cost alerts and attribution. (7) **FinOps:** Culture of cost awareness.

**Q18: What is GitOps?**
A: GitOps uses Git as single source of truth for infrastructure: (1) **Declarative:** Infrastructure defined in Git. (2) **Versioned:** Full history and audit trail. (3) **Automated:** Agents apply changes automatically. (4) **Observed:** Continuous reconciliation. Tools: ArgoCD, Flux. Benefits: Standard Git workflow for infrastructure, rollback capability, drift detection.

**Q19: How do you handle secrets management?**
A: Secrets management: (1) **Never hardcode:** No secrets in code. (2) **Vault:** Use dedicated secret management (HashiCorp Vault, AWS Secrets Manager). (3) **Rotation:** Automatic credential rotation. (4) **Access Control:** Least privilege access to secrets. (5) **Audit:** Log all secret access. (6) **Injection:** Pass secrets at runtime, not in images. Pattern: Apps request secrets from vault at startup.

**Q20: What's the difference between stateful and stateless services?**
A: **Stateless:** No client state stored locally. Pros: Easy to scale horizontally, fault-tolerant, simple to deploy. **Stateful:** Maintains client session/data. Pros: Performance (data local), simpler for some use cases. Stateless preferred: Enables elasticity, resilience. Stateful handling: Externalize state to database, cache, or object storage.

### Category 3: SECURITY ARCHITECTURE (10 FAQs)

**Q21: What is defense in depth?**
A: Defense in depth: Multiple security layers so if one fails, others protect. Layers: (1) **Physical:** Data center security. (2) **Network:** Firewalls, segmentation, VPN. (3) **Host:** OS hardening, endpoint protection. (4) **Application:** Input validation, authentication. (5) **Data:** Encryption, access control. (6) **Identity:** MFA, least privilege. Principle: No single point of failure in security.

**Q22: How do you design secure APIs?**
A: API security: (1) **Authentication:** Verify identity (OAuth 2.0, JWT). (2) **Authorization:** Check permissions (RBAC, ABAC). (3) **Input Validation:** Sanitize all input. (4) **Rate Limiting:** Prevent abuse. (5) **HTTPS:** Encrypt in transit (TLS 1.3). (6) **Logging:** Audit all access. (7) **Versioning:** Deprecate old versions. (8) **Documentation:** Don't expose internals.

**Q23: What is zero trust architecture?**
A: Zero Trust: "Never trust, always verify." Principles: (1) **Verify explicitly:** Authenticate and authorize every access. (2) **Least privilege:** Minimum access needed. (3) **Assume breach:** Limit blast radius. Implementation: Identity verification, device health checks, micro-segmentation, encryption everywhere. Contrast: Traditional perimeter security (trusted inside, untrusted outside).

**Q24: How do you approach threat modeling?**
A: Threat modeling process: (1) **Identify Assets:** What needs protection? (2) **Architecture:** Diagram the system. (3) **Threats:** Identify threats (STRIDE: Spoofing, Tampering, Repudiation, Info disclosure, DoS, Elevation). (4) **Mitigation:** Design countermeasures. (5) **Validate:** Review and test. When: Early design phase, for significant changes. Tools: Microsoft Threat Modeling Tool, OWASP Threat Dragon.

**Q25: What is the principle of least privilege?**
A: Least privilege: Users/systems have minimum access needed to function. Application: (1) **Identity:** No default admin access. (2) **Service accounts:** Specific permissions per service. (3) **Temporary:** Time-bound access. (4) **Just-in-time:** Access granted when needed, revoked after. (5) **Regular review:** Periodic access audits. Benefit: Limits damage from compromised accounts.

**Q26: How do you secure microservices?**
A: Microservices security: (1) **Service-to-service:** mTLS for internal communication. (2) **API Gateway:** Single entry point, centralized auth. (3) **Identity:** Service accounts and workload identity. (4) **Secrets:** Centralized secret management. (5) **Network:** Segmentation, service mesh security. (6) **Observability:** Security monitoring and anomaly detection. (7) **Scanning:** Container and dependency scanning.

**Q27: What is data encryption at rest and in transit?**
A: **In Transit:** Data encrypted while moving (TLS/SSL for network traffic). **At Rest:** Data encrypted when stored (database encryption, file encryption). Implementation: (1) **Key Management:** Secure key storage and rotation. (2) **Algorithm:** AES-256 for symmetric, RSA-2048+ for asymmetric. (3) **Implementation:** Use vetted libraries, never roll your own. Compliance: Required for GDPR, HIPAA, PCI-DSS.

**Q28: How do you handle security in CI/CD pipelines?**
A: DevSecOps practices: (1) **Shift Left:** Security testing early in pipeline. (2) **SAST:** Static analysis for code vulnerabilities. (3) **DAST:** Dynamic testing of running apps. (4) **Dependency Scanning:** Check for known vulnerabilities. (5) **Container Scanning:** Image vulnerability assessment. (6) **Secrets Detection:** Prevent credential leakage. (7) **IaC Scanning:** Check infrastructure templates.

**Q29: What is security by design?**
A: Security by design: Build security in from start, not bolt on later. Principles: (1) **Default Secure:** Secure defaults, explicit opening. (2) **Fail Secure:** Fail to safe state. (3) **Complete Mediation:** Check every access. (4) **Economy of Mechanism:** Simpler = more secure. (5) **Open Design:** Security shouldn't depend on secrecy. (6) **Least Privilege:** Minimum necessary access.

**Q30: How do you respond to security incidents?**
A: Incident response: (1) **Preparation:** Plan, tools, team ready. (2) **Detection:** Identify incidents quickly. (3) **Containment:** Limit damage (short-term then long-term). (4) **Eradication:** Remove threat. (5) **Recovery:** Restore systems. (6) **Lessons Learned:** Post-incident review. Document: Incident response plan, playbooks, communication templates.

### Category 4: PERFORMANCE & SCALABILITY (10 FAQs)

**Q31: How do you design for scalability?**
A: Scalability patterns: (1) **Horizontal Scaling:** Add more instances (stateless services). (2) **Load Balancing:** Distribute traffic. (3) **Caching:** Reduce database load (Redis, CDN). (4) **Database Scaling:** Read replicas, sharding, partitioning. (5) **Async Processing:** Queue heavy work. (6) **Auto-scaling:** Automatic capacity adjustment. (7) **Efficiency:** Optimize code and queries.

**Q32: What is the difference between latency and throughput?**
A: **Latency:** Time to complete single request (milliseconds). Important for: User experience, real-time systems. **Throughput:** Number of requests processed per second (requests/second). Important for: Batch processing, overall capacity. Relationship: Often inverse; optimizing for one may impact other. Measure both: p50, p95, p99 for latency; sustained and peak for throughput.

**Q33: How do you approach caching strategy?**
A: Caching layers: (1) **Browser:** HTTP caching headers. (2) **CDN:** Static content caching. (3) **Application:** In-memory caching (Redis). (4) **Database:** Query result caching. Strategies: (1) **Cache-Aside:** App manages cache. (2) **Read-Through:** Cache fetches if missing. (3) **Write-Through:** Write to cache and DB. (4) **Write-Behind:** Async write to DB. Invalidation: TTL, event-driven, or manual.

**Q34: What is database sharding?**
A: Sharding: Split data across multiple databases. Types: (1) **Horizontal:** Rows distributed (user ID range). (2) **Vertical:** Columns separated (hot vs. cold data). (3) **Directory-Based:** Lookup service routes queries. Challenges: Cross-shard queries, rebalancing, hot spots. Use when: Single database can't handle load or storage.

**Q35: How do you handle high write throughput?**
A: Write-heavy patterns: (1) **Batching:** Group writes. (2) **Async:** Queue writes, process asynchronously. (3) **CQRS:** Separate read and write models. (4) **Event Sourcing:** Append-only event log. (5) **Write-Optimized DB:** Use appropriate database (Cassandra, DynamoDB). (6) **Partitioning:** Distribute write load. (7) **Backpressure:** Control incoming request rate.

**Q36: What is a content delivery network (CDN)?**
A: CDN distributes content geographically: (1) **Edge Servers:** Cache content close to users. (2) **Origin Shield:** Reduce origin load. (3) **Dynamic Acceleration:** Optimize dynamic content. (4) **DDoS Protection:** Absorb attacks. Providers: Cloudflare, Akamai, AWS CloudFront, Fastly. Use for: Static assets, video streaming, global applications.

**Q37: How do you measure and optimize performance?**
A: Performance engineering: (1) **Metrics:** Latency percentiles, throughput, error rate, resource utilization. (2) **Profiling:** CPU, memory, I/O analysis. (3) **Load Testing:** Simulate production traffic. (4) **Chaos Engineering:** Test failure scenarios. (5) **APM:** Application performance monitoring. (6) **Tracing:** Distributed request tracing. Optimize: Measure → Identify bottleneck → Optimize → Validate.

**Q38: What is backpressure in distributed systems?**
A: Backpressure: Control flow when consumer can't keep up with producer. Mechanisms: (1) **Rate Limiting:** Throttle requests. (2) **Buffering:** Queue with limits. (3) **Shedding:** Drop excess load. (4) **Load Shedding:** Reject low-priority requests. (5) **Circuit Breaker:** Fail fast when downstream struggling. Goal: Graceful degradation, not cascade failure.

**Q39: How do you design for low latency?**
A: Low latency techniques: (1) **Caching:** Avoid database calls. (2) **Connection Pooling:** Reuse connections. (3) **Async Processing:** Don't wait for non-critical work. (4) **Edge Computing:** Process close to user. (5) **Binary Protocols:** gRPC vs. HTTP/JSON. (6) **Pre-computation:** Calculate ahead of time. (7) **Efficient Algorithms:** Optimize hot paths. Measure: p99 latency, not just average.

**Q40: What is load shedding?**
A: Load shedding: Intentionally drop traffic to preserve system stability. Implementation: (1) **Priority Queue:** Process high-priority first. (2) **Rate Limiting:** Max requests per client. (3) **Request Classification:** Identify essential vs. deferrable. (4) **Graceful Degradation:** Reduce functionality. Trigger: Resource thresholds (CPU, memory, queue depth). Goal: Survive traffic spikes without total failure.

### Category 5: TECHNICAL LEADERSHIP (10 FAQs)

**Q41: How do you balance innovation with stability?**
A: Innovation-stability balance: (1) **Golden Path:** Recommended, supported stack for most teams. (2) **Innovation Time:** Dedicated time for experimentation. (3) **Pilots:** Test new tech with limited scope. (4) **Graduation:** Promote successful pilots to golden path. (5) **Sunset:** Deprecate outdated tech. (6) **Risk Assessment:** Evaluate production readiness. Rule: "Boring" tech for critical paths; innovation for differentiation.

**Q42: What makes an effective architecture review?**
A: Effective reviews: (1) **Timing:** Early (before significant investment). (2) **Context:** Business goals and constraints clear. (3) **Stakeholders:** Right people (builders, operators, security). (4) **Structure:** Alternatives considered, trade-offs explicit. (5) **ADRs:** Documented decision records. (6) **Non-Functional:** Performance, security, scalability requirements. (7) **Follow-up:** Implementation verification. Culture: Constructive, learning-focused.

**Q43: How do you drive technical excellence across teams?**
A: Technical excellence: (1) **Standards:** Clear, documented expectations. (2) **Training:** Skill development programs. (3) **Reviews:** Code and architecture reviews. (4) **Metrics:** Quality metrics visible to all. (5) **Tooling:** Automated quality checks. (6) **Recognition:** Celebrate excellence. (7) **Time:** Allocate time for refactoring. (8) **Leadership:** Lead by example.

**Q44: What is the role of prototypes and POCs?**
A: Prototypes/POCs: Validate assumptions before full investment. Use: (1) **New Technology:** Does it work for our use case? (2) **Complex Integration:** Can systems connect? (3) **Performance:** Will it meet requirements? (4) **User Experience:** Will users adopt? Scope: Time-bound, limited scope, throwaway or evolutionary. Success criteria defined upfront.

**Q45: How do you make build vs. buy decisions?**
A: Build vs. buy framework: **Build:** Core differentiator, unique requirements, strategic capability, no viable vendor. **Buy:** Commodity capability, faster time-to-market, vendor expertise, lower TCO. **Hybrid:** Buy core, build integration/customization. Evaluation: TCO analysis, strategic fit, time-to-value, risk, team capacity.

**Q46: What is the role of an Architecture Decision Record (ADR)?**
A: ADRs document significant architectural decisions: (1) **Context:** Why decision needed. (2) **Decision:** What was decided. (3) **Consequences:** Trade-offs and implications. (4) **Status:** Proposed, accepted, deprecated, superseded. Benefits: Knowledge preservation, decision transparency, onboarding aid, change tracking. Format: Lightweight Markdown files in repository.

**Q47: How do you manage technology lifecycle?**
A: Technology lifecycle: (1) **Evaluate:** Assess emerging technologies. (2) **Pilot:** Limited production use. (3) **Adopt:** Standard for appropriate use cases. (4) **Maintain:** Standard support. (5) **Deprecate:** No longer recommended for new use. (6) **Retire:** Remove from production. Governance: Technology radar, review board, clear ownership.

**Q48: What is platform engineering?**
A: Platform engineering: Build internal platforms to accelerate product teams. Components: (1) **Self-Service:** Teams provision resources independently. (2) **Golden Path:** Easy, approved way to do common tasks. (3) **Abstraction:** Hide infrastructure complexity. (4) **Standards:** Enforced by platform, not documents. (5) **Observability:** Built-in monitoring and logging. Goal: Developer productivity and organizational efficiency.

**Q49: How do you approach technical documentation?**
A: Documentation strategy: (1) **Architecture:** C4 diagrams, ADRs. (2) **API:** OpenAPI specs, generated docs. (3) **Runbooks:** Operational procedures. (4) **README:** Repo setup and usage. (5) **Decision Records:** Why, not just what. (6) **Wikis:** Living knowledge. Principles: Close to code, version controlled, maintained, discoverable.

**Q50: How do you scale technical decision-making?**
A: Decision scaling: (1) **Principles:** Clear, communicated guidelines. (2) **Patterns:** Reusable solutions for common problems. (3) **Empowerment:** Delegate decisions to teams within guardrails. (4) **Review Board:** For significant cross-cutting decisions. (5) **RACI:** Clear decision ownership. (6) **Automation:** Codify decisions in tools and platforms. Goal: Fast local decisions, alignment on global decisions.

# SECTION 5: SOPs & STANDARD OPERATING PROCEDURES

## SOP 1: Architecture Design Process

**Duration:** 1-2 weeks | **Frequency:** Per major feature/system | **Owner:** CTO

1. **Requirements Gathering:** Business needs, constraints, non-functional requirements
2. **Current State Analysis:** Existing systems, dependencies, technical debt
3. **Option Exploration:** Research patterns, technologies, approaches
4. **Design Sessions:** Collaborative design with stakeholders

- Implementation roadmap

## SOP 2: Technology Evaluation & Selection

**Duration:** 2-4 weeks | **Frequency:** As needed | **Owner:** CTO

4. **Shortlisting:** Preliminary filter based on requirements
