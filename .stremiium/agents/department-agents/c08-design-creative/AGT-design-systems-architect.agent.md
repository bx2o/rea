# SECTION 4: KEY FAQS & KNOWLEDGE LIBRARY

## 4.1 Design System FAQs

**Q1: What belongs in a design system vs. custom design?**
A: **In system:** Common patterns (buttons, inputs, navigation), foundations (colors, type, spacing), recurring layouts. **Custom:** Unique features, one-off marketing pages, experimental concepts. Rule: If used 3+ times or by multiple teams, consider system. Balance: System enables efficiency but shouldn't stifle creativity or unique needs.

**Q2: How do you prioritize what to build?**
A: Framework: (1) **Usage frequency:** Most-used patterns first. (2) **Impact:** High-visibility, critical user flows. (3) **Complexity:** Harder to get right = higher value in system. (4) **Requests:** What teams are asking for. (5) **Strategic:** What supports company priorities. (6) **Effort:** Balance value vs. effort. Start with highest-frequency, highest-impact components.

**Q3: How do you handle design system versioning?**
A: Strategy: (1) **Semantic versioning:** Major (breaking), minor (new features), patch (fixes). (2) **Changelog:** Document all changes. (3) **Migration guides:** Help teams upgrade. (4) **Deprecation:** Warn before removing. (5) **Support window:** Maintain old versions for transition period. (6) **Communication:** Announce changes proactively.

**Q4: What's the relationship between design and code components?**
A: **Parity goal:** Design components should match code 1:1. **Shared language:** Same names, same API. **Sync process:** Design updates trigger code updates. **Single source:** Tokens shared between design and code. **Tools:** Figma + Storybook integration. Reality: 100% parity is ideal; document where design and code diverge.

**Q5: How do you maintain system quality?**
A: Practices: (1) **Standards:** Clear contribution criteria. (2) **Review process:** Peer review for all additions. (3) **Testing:** Visual regression, accessibility checks. (4) **Documentation:** Every component fully documented. (5) **Usage monitoring:** Track adoption and issues. (6) **Feedback loop:** Issues and requests triaged. (7) **Maintenance budget:** Allocate time for system upkeep.

## 4.2 Implementation FAQs

**Q6: How do you measure design system success?**
A: Metrics: (1) **Adoption:** % of UI using system components. (2) **Efficiency:** Time to create designs, implement features. (3) **Consistency:** Brand/design compliance scores. (4) **Satisfaction:** Designer/developer NPS. (5) **Coverage:** % of UI patterns in system. (6) **Contribution:** Internal contributions and engagement.

**Q7: How do you handle requests for system changes?**
A: Process: (1) **Intake:** Request template with context. (2) **Triage:** Review against principles and roadmap. (3) **Prioritization:** Rank by impact and effort. (4) **Design:** Create/update component. (5) **Review:** System team and stakeholders. (6) **Release:** Update libraries and documentation. (7) **Communicate:** Announce to users.

# SECTION 5: STANDARD OPERATING PROCEDURES

## SOP 1: Component Development

**Duration:** 2-4 weeks | **Frequency:** Per component

1. **Request:** Identify need through intake
2. **Research:** Audit existing usage, competitive analysis
3. **Design:** Create component with all states
4. **Spec:** Document behavior, API, usage
5. **Review:** System team and stakeholder review
6. **Iterate:** Refine based on feedback
7. **Document:** Write comprehensive docs
8. **Release:** Publish to design library and code
9. **Announce:** Communicate to teams
10. **Support:** Answer questions, gather feedback

## SOP 2: System Audit

**Duration:** 1-2 weeks | **Frequency:** Quarterly

1. **Inventory:** List all product screens
2. **Map:** Identify components used vs. custom
3. **Gap analysis:** What's missing from system
4. **Consistency check:** Off-brand or inconsistent usage
5. **Quality review:** Component implementation quality
6. **Report:** Share findings with teams
7. **Plan:** Prioritize updates and additions

## SOP 3: Design Token Management

**Duration:** Ongoing | **Frequency:** As needed

1. **Audit:** Review current token usage
2. **Propose:** New tokens or changes
3. **Review:** Impact analysis across system
4. **Update:** Design tokens in Figma
5. **Sync:** Update code tokens
6. **Test:** Verify changes propagate
7. **Document:** Update token documentation
8. **Communicate:** Notify teams of changes
