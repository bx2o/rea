# SECTION 4: KEY FAQS & KNOWLEDGE LIBRARY

## 4.1 Thirty+ Frequently Asked Questions

### Category 1: DEVOPS & CI/CD (6 FAQs)

**Q1: What is DevOps?**
A: DevOps is culture, practices, and tools that integrate development and operations. Goals: (1) **Speed:** Faster deployments. (2) **Reliability:** Fewer failures. (3) **Scale:** Manage complex systems. (4) **Security:** Shift-left security. Practices: CI/CD, IaC, monitoring, collaboration. Not just tools—cultural transformation.

**Q2: What is CI/CD?**
A: **CI (Continuous Integration):** Automate build and test on every commit. **CD (Continuous Delivery):** Automate deployment to staging. **CD (Continuous Deployment):** Automate deployment to production. Benefits: Fast feedback, reduced risk, faster time to market. Pipeline: Code → Build → Test → Deploy → Monitor.

**Q3: How do you implement zero-downtime deployments?**
A: Deployment strategies: (1) **Blue-Green:** Two identical environments, switch traffic. (2) **Canary:** Deploy to small subset, monitor, expand. (3) **Rolling:** Replace instances gradually. (4) **Feature Flags:** Deploy code disabled, enable gradually. Prerequisites: Health checks, monitoring, rollback plan.

**Q4: What is GitOps?**
A: GitOps uses Git as source of truth for infrastructure and applications: (1) **Declarative:** System state defined in Git. (2) **Versioned:** Full history and audit. (3) **Automated:** Agents apply changes. (4) **Observed:** Continuous reconciliation. Tools: ArgoCD, Flux. Benefits: Standard Git workflow, rollback, drift detection.

**Q5: How do you manage deployment risk?**
A: Risk mitigation: (1) **Testing:** Comprehensive automated tests. (2) **Staging:** Production-like environment. (3) **Progressive:** Canary or gradual rollout. (4) **Feature Flags:** Kill switches for features. (5) **Monitoring:** Detect issues fast. (6) **Rollback:** One-click revert. (7) **Post-Deploy:** Watch metrics after release.

**Q6: What makes a good CI/CD pipeline?**
A: Pipeline characteristics: (1) **Fast:** Feedback in minutes. (2) **Reliable:** Consistent results. (3) **Comprehensive:** Test all critical paths. (4) **Isolated:** No external dependencies. (5) **Parallel:** Run tests concurrently. (6) **Informative:** Clear pass/fail with details. (7) **Secure:** Secrets managed, scan for vulnerabilities.

### Category 2: INFRASTRUCTURE (6 FAQs)

**Q7: What is Infrastructure as Code (IaC)?**
A: IaC manages infrastructure through code: (1) **Declarative:** Define desired state (Terraform, CloudFormation). (2) **Versioned:** Git history and review. (3) **Reproducible:** Same result every time. (4) **Testable:** Validate before apply. (5) **Documented:** Code is documentation. Best practices: Modular, state management, no secrets in code.

**Q8: When should you use Kubernetes?**
A: Use Kubernetes when: (1) **Scale:** Many microservices. (2) **Complexity:** Complex deployment needs. (3) **Portability:** Multi-cloud requirements. (4) **Efficiency:** High resource utilization. (5) **Team:** SRE/DevOps expertise available. Don't use: Simple applications, small scale, limited expertise. Managed services (EKS, GKE, AKS) reduce overhead.

**Q9: How do you manage cloud costs?**
A: Cost management: (1) **Tagging:** Every resource labeled. (2) **Showback:** Visibility to teams. (3) **Right-sizing:** Match resources to usage. (4) **Reserved:** Commit for steady workloads. (5) **Spot:** Use preemptible for fault-tolerant. (6) **Auto-scaling:** Scale down when idle. (7) **Monitoring:** Alerts for anomalies. (8) **Governance:** Policies prevent waste.

**Q10: What is multi-region architecture?**
A: Multi-region strategies: (1) **Active-Passive:** Primary region, DR secondary. (2) **Active-Active:** Traffic split across regions. (3) **Geo-Routing:** Route to nearest region. Benefits: Disaster recovery, latency reduction, compliance. Challenges: Data replication, consistency, complexity, cost.

**Q11: How do you handle secrets management?**
A: Secrets management: (1) **Never hardcode:** No secrets in code or config. (2) **Vault:** Use dedicated secret store (HashiCorp Vault, AWS Secrets Manager). (3) **Rotation:** Automatic credential rotation. (4) **Access:** Least privilege, audit access. (5) **Injection:** Runtime injection, not in images. (6) **Encryption:** At rest and in transit.

**Q12: What is service mesh?**
A: Service mesh (Istio, Linkerd) manages service-to-service communication: (1) **mTLS:** Automatic encryption. (2) **Traffic:** Routing, splitting, retries. (3) **Observability:** Metrics, tracing. (4) **Security:** Policies, auth. (5) **Resilience:** Circuit breakers, timeouts. Trade-off: Adds complexity and latency. Use when: Many microservices, complex traffic needs.

### Category 3: OBSERVABILITY (6 FAQs)

**Q13: What is observability?**
A: Observability is understanding system state from outputs: (3) **Metrics:** Numeric data over time (Prometheus). (2) **Logs:** Event records (ELK). (3) **Traces:** Request flows (Jaeger). Difference from monitoring: Monitoring tells you when something is wrong, observability helps you understand why. Goal: Debug unknown-unknowns.

**Q14: What are SLOs, SLIs, and SLAs?**
A: **SLI (Service Level Indicator):** Metric measuring service (e.g., availability %). **SLO (Service Level Objective):** Target for SLI (e.g., 99.9% availability). **SLA (Service Level Agreement):** Contract with consequences (often external). Usage: SLOs drive engineering priorities; error budgets balance reliability vs. velocity.

**Q15: How do you reduce alert fatigue?**
A: Alert quality principles: (1) **Actionable:** Every alert needs response. (2) **Relevant:** Page the right team. (3) **No Flapping:** Stable, not oscillating. (4) **Bunched:** Group related alerts. (5) **Prioritized:** Severity appropriate. (6) **Documented:** Runbook linked. Process: Regular alert review, remove low-value alerts.

**Q16: What is distributed tracing?**
A: Distributed tracing follows requests across services: (1) **Trace:** End-to-end request journey. (2) **Span:** Single operation within trace. (3) **Context:** Propagated across services. Benefits: Latency analysis, dependency mapping, bottleneck identification. Tools: Jaeger, Zipkin, AWS X-Ray, Datadog APM.

**Q17: How do you build effective dashboards?**
A: Dashboard design: (1) **Purpose:** Clear audience and goal. (2) **Hierarchy:** Most important at top. (3) **Real-time:** Live data when needed. (4) **Context:** Trends and comparisons. (5) **Actionable:** Leads to decisions. (6) **DRY:** Don't duplicate existing dashboards. (7) **Mobile:** Works on all screens.

**Q18: What is log aggregation?**
A: Log aggregation centralizes logs from all systems: (1) **Collection:** Ship logs to central system. (2) **Storage:** Retain with appropriate lifecycle. (3) **Search:** Full-text search capability. (4) **Analysis:** Pattern detection. (5) **Alerting:** Trigger on log patterns. Tools: ELK stack, Splunk, Datadog, Grafana Loki. Best practice: Structured logging (JSON).

### Category 4: RELIABILITY (6 FAQs)

**Q19: What is SRE (Site Reliability Engineering)?**
A: SRE applies software engineering to operations: (1) **SLOs:** Define reliability targets. (2) **Error Budgets:** Balance reliability and velocity. (3) **Toil Reduction:** Automate manual work. (4) **Blameless Postmortems:** Learn from failures. (5) **Monitoring:** Measure what matters. Book: Google's SRE book. Goal: Reliability through engineering, not operations.

**Q20: How do you run an incident response?**
A: Incident response phases: (1) **Detect:** Monitoring alerts. (2) **Page:** Notify on-call. (3) **Assess:** Severity and scope. (4) **Mitigate:** Reduce impact. (5) **Resolve:** Fix root cause. (6) **Postmortem:** Learn and improve. Role: Incident Commander coordinates. Tools: PagerDuty, Opsgenie, incident.io.

**Q21: What is a blameless postmortem?**
A: Blameless postmortem focuses on system and process, not people: (1) **Timeline:** What happened when. (2) **Detection:** How did we find out? (3) **Impact:** Who was affected? (4) **Root Causes:** 5 Whys analysis. (5) **Action Items:** Prevent recurrence. (6) **Share:** Document for organization. Goal: Learn, don't punish.

**Q22: How do you implement chaos engineering?**
A: Chaos engineering tests resilience by injecting failures: (1) **Define steady state:** Normal behavior. (2) **Hypothesize:** What happens if...? (3) **Inject:** Introduce failure (kill instance, latency, error). (4) **Monitor:** Observe system response. (5) **Rollback:** Stop experiment. (6) **Improve:** Fix weaknesses. Tools: Gremlin, Chaos Monkey, Litmus.

**Q23: What is an error budget?**
A: Error budget: Acceptable unreliability (e.g., 0.1% for 99.9% SLO). Usage: If budget remaining, deploy aggressively. If budget spent, freeze features, focus on reliability. Balances: Engineering velocity vs. service reliability. Reset: Typically monthly or quarterly.

**Q24: How do you build disaster recovery?**
A: DR planning: (1) **RTO:** Recovery Time Objective (how fast). (2) **RPO:** Recovery Point Objective (data loss). (3) **Backup:** Regular, tested backups. (4) **Replication:** Real-time data sync. (5) **Runbook:** Step-by-step procedures. (6) **Testing:** Regular DR drills. (7) **Multi-region:** Geographic distribution.

### Category 5: PLATFORM & OPERATIONS (6 FAQs)

**Q25: What is platform engineering?**
A: Platform engineering builds internal platforms for developer productivity: (1) **Self-service:** Teams provision independently. (2) **Golden path:** Easy, approved way. (3) **Abstraction:** Hide complexity. (4) **Standards:** Enforced by platform. (5) **Observability:** Built-in monitoring. Benefits: Faster development, consistency, reduced cognitive load.

**Q26: How do you measure engineering productivity?**
A: DORA metrics: (1) **Deployment Frequency:** How often deploy. (2) **Lead Time:** Time from commit to production. (3) **Change Failure Rate:** % of deployments causing failure. (4) **MTTR:** Time to recover from failure. SPACE framework: Satisfaction, Performance, Activity, Communication, Efficiency. Avoid: Individual performance metrics.

**Q27: What is FinOps?**
A: FinOps brings financial accountability to cloud: (1) **Inform:** Visibility into spend. (2) **Optimize:** Right-size, reserved instances, spot. (3) **Operate:** Continuous improvement. Team: Engineers, finance, business together. Goal: Maximize cloud value, not just minimize cost.

**Q28: How do you manage on-call?**
A: On-call best practices: (1) **Rotation:** Fair distribution. (2) **Escalation:** Clear path if stuck. (3) **Compensation:** Pay for on-call time. (4) **Runbooks:** Documented procedures. (5) **Alert quality:** Reduce noise. (6) **Post-incident:** Handoff notes. (7) **Well-being:** Prevent burnout.

**Q29: What is configuration management?**
A: Configuration management maintains consistent system state: (1) **Desired state:** Defined in code. (2) **Drift detection:** Identify deviations. (3) **Remediation:** Auto-correct or alert. Tools: Ansible, Chef, Puppet. Container era: Kubernetes handles much of this. IaC: Terraform for infrastructure.

**Q30: How do you balance build vs. buy for infrastructure?**
A: Decision criteria: **Build:** Core differentiator, unique needs, strategic capability. **Buy:** Commodity, faster time-to-value, vendor expertise, lower TCO. **Hybrid:** Buy core, customize integration. Evaluate: Cost, time, risk, team capacity, strategic importance.

# SECTION 5: SOPs & STANDARD OPERATING PROCEDURES

## SOP 1: Incident Response

**Duration:** Variable | **Frequency:** As needed | **Owner:** On-Call Engineer

1. **Detect:** Alert or report received
2. **Acknowledge:** Claim incident within 5 minutes
3. **Assess:** Severity, impact, scope
4. **Page:** Escalate if needed
5. **Communicate:** Status page, stakeholders
6. **Mitigate:** Reduce impact (not necessarily fix)
7. **Resolve:** Restore service
8. **Monitor:** Watch for recurrence
9. **Postmortem:** Schedule within 48 hours
10. **Follow-up:** Complete action items

**Severity Levels:**

- SEV1: Complete outage, revenue impact
- SEV2: Major functionality degraded
- SEV3: Minor impact, workaround available
- SEV4: Cosmetic or monitoring only

## SOP 2: Production Deployment

**Duration:** 30 min - 2 hours | **Frequency:** Daily | **Owner:** Release Engineer

1. **Pre-Deploy Checklist:** Tests pass, review complete
2. **Staging Deploy:** Deploy to staging, validate
3. **Production Deploy:** Execute deployment plan
4. **Smoke Tests:** Automated health checks
5. **Monitoring Watch:** Observe metrics for 30 min
6. **Rollback Plan:** Ready if issues detected
7. **Verification:** Confirm success with stakeholders
8. **Documentation:** Update deployment log
9. **Follow-up:** Monitor for 24 hours

**Deployment Types:**

- Standard: Automated pipeline
- Hotfix: Expedited for critical fixes
- Maintenance: Planned infrastructure changes
- Emergency: Break-glass for SEV1

## SOP 3: Capacity Planning

**Duration:** 1 week | **Frequency:** Quarterly | **Owner:** Infrastructure Lead

1. **Data Collection:** Current usage, growth trends
2. **Forecasting:** Project 3-6-12 month needs
3. **Traffic Patterns:** Seasonality, events
4. **Headroom Analysis:** Required buffer
5. **Cost Modeling:** Options and pricing
6. **Plan Creation:** Procurement and scaling plan
7. **Review:** Engineering and finance approval
8. **Execution:** Implement plan
9. **Monitoring:** Track against plan
10. **Adjust:** Update based on actuals

**Deliverables:**

- Capacity forecast
- Resource plan
- Budget impact
- Risk assessment
