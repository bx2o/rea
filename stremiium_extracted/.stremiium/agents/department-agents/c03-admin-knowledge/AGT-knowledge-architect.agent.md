# SECTION 4: FIFTY+ FAQS, SKILLS & KNOWLEDGE LIBRARY

## 4.1 Fifty+ Frequently Asked Questions (FAQs)

### **Category 1: KNOWLEDGE MANAGEMENT SYSTEMS (14 FAQs)**

**Q1: What's the difference between a knowledge base and a wiki?**
A: **Wiki** (e.g., Confluence, MediaWiki): Collaborative, editable by all (with permissions). Good for internal knowledge. **Knowledge base** (e.g., Zendesk, Freshdesk): Curated, organized by topic. Good for customer-facing info. Both: Searchable, interconnected. For internal company knowledge: Wiki usually better (collaborative, fast to update). For customer-facing: Knowledge base (professional, organized). Hybrid: Many companies use both.

**Q2: How do you organize knowledge so people find it?**
A: Structure: (1) **Hierarchical:** Main categories → subcategories → articles. (2) **Task-based:** Organize by what user wants to do ("How to onboard new employee?"). (3) **Topic-based:** Organize by topic (Sales, Engineering, HR). (4) **Audience-based:** Different views for different audiences. Tags: Use consistent tags (so articles discoverable). Search: Good search engine + metadata. Recommendation: Start with task-based (user-centric) structure + tags.

**Q3: When should you create documentation?**
A: Timing: **Before:** Document processes before they become muscle memory (easier to remember). **During:** Capture knowledge as you build (easier than retroactive). **During onboarding:** Ask new employees what wasn't documented (gap identification). **Before departure:** Interview departing employees (capture tribal knowledge). Frequency: Review/update annually + when process changes. Avoid: Waiting until "perfect"; good documentation early > perfect documentation late.

**Q4: What types of documentation should every company have?**
A: Core docs: (1) **Processes:** Step-by-step how to do things (hiring, customer onboarding, product release). (2) **Policies:** Rules (code of conduct, remote work, benefits). (3) **Decisions:** Major decisions + reasoning (ADRs - Architecture Decision Records). (4) **Best practices:** How we do things well (code style, writing, design). (5) **Organizational:** Org structure, team descriptions, accountability. (6) **Get started:** Onboarding guide, first day checklist. (7) **Product:** Feature docs, API docs, user guides. Start: Top 10 processes + organizational docs. Expand: Add as needed.

**Q5: What's an Architecture Decision Record (ADR)?**
A: ADR: Document for significant decisions + reasoning. Contents: (1) **Context:** What's the situation? Why deciding now? (2) **Options considered:** What alternatives? (3) **Decision:** What did we choose? (4) **Rationale:** Why? (5) **Consequences:** What changes as a result? Format: 1-2 pages. Use: For technical decisions (architecture, tech stack), process decisions (hiring approach), business decisions (market strategy). Value: Future person understands "why" without asking. Best practice: Every significant decision = ADR.

**Q6: How do you keep documentation up-to-date?**
A: Challenge: Docs get stale. Solutions: (1) **Owner assignment:** Each doc has owner responsible for accuracy. (2) **Review schedule:** Owner reviews docs quarterly/annually. (3) **Notifications:** System alerts when doc is old ("Last updated 6 months ago"). (4) **Change triggers:** When process changes, team updates doc immediately. (5) **Metrics:** Track documentation freshness (% docs reviewed in last 12 months). (6) **Culture:** Emphasize that stale docs are worse than no docs. (7) **Incentives:** Reward team for maintaining docs. Goal: 90%+ of docs current.

**Q7: What's a taxonomy and why does it matter?**
A: Taxonomy: Organized classification of information. Example: Products → Category (Software, Services) → Product Name. Matters: (1) **Organization:** Logical structure. (2) **Search:** Taxonomy enables good search/filtering. (3) **Growth:** Scales as company grows (100 docs vs. 10,000 docs). (4) **Consensus:** Team agrees on terms (consistency). Start simple: Main categories + subcategories. Evolve: Refine as knowledge base grows. Tools: Wiki systems help manage taxonomy.

**Q8: How do you migrate knowledge when changing systems?**
A: Process: (1) **Assessment:** What knowledge exists? Quality? Format? (2) **Tool selection:** New system chosen. (3) **Mapping:** How does old structure map to new structure? (4) **Migration plan:** Timeline, resources, risk. (5) **Data migration:** Automated (if possible) or manual export/import. (6) **Validation:** Check: Were all docs migrated? Format correct? Links work? (7) **Training:** Teach team new system. (8) **Cutover:** Old system retired. (9) **Monitoring:** Resolve issues post-migration. Timeline: 2-8 weeks depending on volume. Risk: Data loss if not careful; test thoroughly before cutover.

**Q9: What's knowledge preservation and why does it matter?**
A: Preservation: Capture knowledge from departing employees before they leave. Matters: (1) **Tribal knowledge loss:** When expert leaves, knowledge goes with them. (2) **Continuity:** Successor has documentation to learn from. (3) **Efficiency:** Don't have to re-learn from scratch. (4) **Quality:** Expert captures their knowledge (more complete than secondhand). Process: (1) Interview departing employee: "What's your knowledge? What should successors know?" (2) Document: Capture in writing. (3) Review: Expert confirms accuracy. (4) Archive: Store for future reference. Timing: During offboarding (last week). Cost: 5-10 hours of interview time. Value: Prevents months of lost productivity.

**Q10: How do you measure knowledge base effectiveness?**
A: Metrics: (1) **Search metrics:** % searches finding relevant results. (2) **Usage:** % of team using knowledge base? Frequency? (3) **Time saved:** How much time does knowledge base save? (vs. asking questions). (4) **Satisfaction:** Do team members rate knowledge base as helpful? (5) **Completeness:** % of processes documented? (6) **Freshness:** % of docs updated in last 12 months? (7) **Onboarding:** Time to productivity for new employees (trending down = good). Tools: Analytics in knowledge base system. Goal: High usage + satisfaction + freshness = effective.
