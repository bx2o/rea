### Standard Operating Procedures

**SOP 1: Production Deployment**

- Trigger: Code ready for production release
- Steps:
  1. Verify all tests passing (unit, integration, e2e)
  2. Review security scan results
  3. Verify monitoring and alerting in place
  4. Check capacity and resource availability
  5. Deploy using CI/CD pipeline
  6. Verify deployment success via smoke tests
  7. Monitor for anomalies during rollout
  8. Keep rollback plan ready
- Responsible Party: DevOps-Engineer + SRE-Lead
- Success Criteria: Successful deployment with zero incidents
- Escalation: SEV1 incident protocol if deployment fails

**SOP 2: Incident Response**

- Trigger: Alert fired or incident reported
- Steps:
  1. Acknowledge incident within 5 minutes
  2. Assess severity (SEV1-4) and impact
  3. Page on-call engineer if SEV1/2
  4. Create incident channel and war room
  5. Communicate to stakeholders per communication plan
  6. Execute mitigation and resolution
  7. Document timeline and actions taken
  8. Schedule post-mortem within 48 hours
- Responsible Party: SRE-Lead (coordinator)
- Success Criteria: MTTR met, stakeholders informed, no recurrence
- Escalation: Executive escalation for SEV1 customer-impacting incidents

**SOP 3: Security Vulnerability Response**

- Trigger: Vulnerability scan, bug bounty, or external report
- Steps:
  1. Assess severity (CVSS score + business impact)
  2. Create security ticket with classification
  3. For critical (CVSS 9+): Immediate patching within 24 hours
  4. For high (CVSS 7-8.9): Patching within 7 days
  5. For medium/low: Scheduled patching in next sprint
  6. Verify fix through re-scan
  7. Document in security log
  8. Update threat model if necessary
- Responsible Party: Security-Engineer
- Success Criteria: All critical/high vulnerabilities remediated within SLA
- Escalation: Cybersecurity-Intel-Squad for coordinated threats

**SOP 4: Cost Optimization Review**

- Trigger: Monthly cost review cycle
- Steps:
  1. Analyze AWS Cost Explorer reports
  2. Identify top cost drivers and anomalies
  3. Review resource utilization metrics
  4. Identify idle or underutilized resources
  5. Evaluate Reserved Instance coverage
  6. Propose optimization opportunities
  7. Implement approved optimizations
  8. Track savings and report to Finance
- Responsible Party: Cloud-Architect
- Success Criteria: 5-10% monthly cost optimization maintained
- Escalation: Finance-Investor-Relations for budget variance >20%

**SOP 5: Capacity Planning**

- Trigger: Quarterly capacity review or growth forecast
- Steps:
  1. Review historical usage trends
  2. Analyze growth projections from Strategy-Growth
  3. Identify bottlenecks and constraints
  4. Model capacity requirements (3-6-12 months)
  5. Plan resource additions
  6. Budget for capacity expansion
  7. Implement capacity increases
  8. Verify capacity meets demand
- Responsible Party: Cloud-Architect + SRE-Lead
- Success Criteria: No capacity-related incidents, optimal resource utilization
- Escalation: Emergency capacity procurement if unplanned growth

  5. Proof of concept for top 2
  6. Make decision and document rationale (ADR)
- Inputs needed: Requirements, budget, technical constraints
- Output: Selected technology with documented justification
- Documentation: Architecture Decision Record (ADR)

**Framework 2: Build vs Buy**

- When to use: Deciding whether to build internally or purchase solution
- Process:
  1. Define problem and requirements
  2. Evaluate commercial solutions (3-5 vendors)
  3. Estimate build effort (time, cost, maintenance)
  4. Compare TCO over 3-5 years
  5. Assess strategic importance and IP considerations
  6. Make decision based on total value
- Inputs needed: Requirements, budget, strategic context
- Output: Build or buy decision with justification
- Documentation: Build vs Buy Analysis document

**Framework 3: Incident Severity Classification**

- When to use: Classifying and responding to incidents
- Process:
  - SEV1: Complete outage, revenue impact, data loss risk
  - SEV2: Major functionality impaired, workarounds available
  - SEV3: Minor functionality impacted, limited users affected
  - SEV4: Cosmetic issues, no user impact
- Inputs needed: Impact assessment, affected systems
- Output: Severity classification and response protocol
- Documentation: Incident ticket with severity label

### Architecture & Design Patterns (15 FAQs)

**Q: When should I use microservices vs monolith?**
A: Microservices for: independent scaling, multiple teams, different tech stacks. Monolith for: small teams, rapid iteration, lower operational overhead.

**Q: What is the preferred database for different use cases?**
A: PostgreSQL for relational data, MongoDB for documents, Redis for caching/sessions, TimescaleDB for time-series, IPFS for decentralized storage.

**Q: How do I design for multi-region availability?**
A: Active-passive for most services (failover), active-active for read-heavy services. Use Route 53 for DNS failover. Replicate data asynchronously.

**Q: What is the circuit breaker pattern and when to use?**
A: Prevents cascade failures by stopping calls to failing services. Use for external dependencies, third-party APIs, services with known instability.

**Q: How do I implement proper secrets management?**
A: Use HashiCorp Vault for all secrets. Never hardcode. Rotate regularly. Audit access. Use dynamic credentials where possible.

**Q: What caching strategy should I use?**
A: Redis for distributed caching. Use cache-aside pattern. Implement cache warming. Set appropriate TTLs. Monitor hit rates.

**Q: How do I handle database migrations safely?**
A: Backward-compatible changes only. Use expand-contract pattern. Test on staging. Have rollback plan. Run during low-traffic windows.

**Q: What is the best way to handle API rate limiting?**
A: Implement token bucket algorithm. Return 429 status with Retry-After header. Monitor rate limit hits. Document limits clearly.

**Q: How should I structure Kubernetes deployments?**
A: Use Helm charts. Separate configs by environment. Implement health checks. Use resource limits. Enable HPA for scaling.

**Q: What is the preferred messaging pattern?**
A: Kafka for high-throughput event streaming. RabbitMQ for task queues. Use dead letter queues. Implement idempotency.

**Q: How do I implement observability in new services?**
A: Structured logging (JSON). OpenTelemetry tracing. Prometheus metrics. Health check endpoints. Correlation IDs for tracing.

**Q: What is the best practice for API versioning?**
A: URL versioning (/v1/, /v2/). Maintain backward compatibility. Deprecate old versions gracefully. Communicate changes early.

**Q: How do I design for compliance (FICA/POPIA)?**
A: Data classification. Encryption at rest and in transit. Access controls. Audit logging. Data residency controls. Regular assessments.

**Q: What is the recommended approach for blockchain integration?**
A: Use managed node providers where possible. Implement retry logic with backoff. Cache blockchain data. Monitor gas prices. Use event indexing.

**Q: How do I handle disaster recovery for critical data?**
A: RPO <1 hour, RTO <4 hours. Cross-region replication. Regular backup testing. Documented runbooks. Automated failover where possible.
